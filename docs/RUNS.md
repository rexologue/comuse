# Запуски

Этот документ описывает, как задача запускается и исполняется: scheduler, runner,
журнал запуска, пробный запуск, уведомления и срок хранения.

**Запуск никогда не ждёт человека** и идёт от начала до конца. Где нужен человек,
команда оставляет результат вне запуска: письмо в черновиках, файл в папке на
проверку.

## Расписание

scheduler решает только «когда». Что делают шаги задачи, он не знает: почту и папки не
читает. «Отвечать на новые письма» — это задача по cron с шагом `mail.search`.

- **Триггеры:** `cron` (5 полей) и `manual` (без расписания — только вручную). Время —
  часовой пояс процесса; в Docker его задаёт `TZ`.
- **Дни недели — только именами** `MON`..`SUN`. Числа APScheduler считает не как
  стандартный cron: `0` — понедельник, `1` — вторник, `7` не принимает. Карточка
  задачи при этом описывает число по стандарту, поэтому `0 9 * * 1` читается «по
  понедельникам», а запускается во вторник.
- **Задания живут в памяти.** Когда запускать задачу, записано в её активной версии,
  поэтому своей таблицы у scheduler нет: при старте он строит задания по всем активным
  задачам, а после одобрения версии или смены статуса задачи main просит его перечитать
  одну задачу (`POST /reload {task_id}`). Задачу, версию которой прочитать не удалось
  (например, собранную по старой схеме), scheduler пропускает с ошибкой в логе и
  планирует остальные.
- **Срабатывание** → `POST main/runner/runs {task_id, trigger: "cron"}`. Срабатывания,
  пропущенные, пока scheduler был остановлен, не догоняются: после старта задания строятся
  заново. Задержки внутри работающего процесса (например, после сна машины) до часа
  сливаются в один запуск.
- `GET /jobs` — задачи по расписанию, их cron и ближайшее время запуска.

## Исполнение

Запуск создаётся через `POST /runs` (см. [API.md](API.md#запуски)): по кнопке
(`trigger: manual`), по расписанию (`cron`) или пробный (`dry_run`). runner:

1. Берёт версию (по `task_id` — активную) и настройки задачи.
2. Считает `variables` (с `today` и `now`).
3. Для каждого шага: проверяет `when`, рендерит `args` (см.
   [TASKS.md](TASKS.md#данные-между-шагами)), вызывает команду через
   `POST main/executor/execute` с `mode: run`, `run_id`, ключом шага, настройками задачи и
   флагом пробного запуска; пишет шаг в журнал.
4. Обрабатывает результат по правилам шага:
   - ошибка: `fail` — запуск падает; `retry` — повтор до `retries` раз с паузой 2, 4, 6…
     секунд; `skip` — шаг пропущен, дальше;
   - пустой результат: `continue`; `fail` — запуск падает; `skip` — делать нечего,
     запуск тихо заканчивается.

Шаги внутри `foreach` получают ключи-пути: `sort[2].move` — шаг `move` для третьего
элемента.

**Один настоящий запуск задачи за раз.** Если предыдущий ещё идёт, новый получает 409;
scheduler пишет это в лог и ждёт следующего срабатывания. Пробные запуски этому не
мешают.

**Отмена:** `POST /runs/{id}/cancel`. Запуск в очереди закрывается сразу, идущий —
перед следующим шагом. Запуски, оставшиеся незаконченными после перезапуска runner,
закрываются как `failed`.

## Статусы

| Статус | Что значит |
| --- | --- |
| `queued` | Создан, ещё не начат |
| `running` | Идёт |
| `succeeded` | Дошёл до конца или тихо закончился по `on_empty: skip` после шага, который что-то вернул |
| `empty` | Все шаги, которые успели выполниться, вернули пустой результат — в том числе ранняя остановка по `on_empty: skip`: проверка ничего не нашла. Только у настоящих запусков |
| `failed` | Шаг упал без `skip`, сбой runner, запуск прерван перезапуском или не уложился во время ожидания (`wait`) |
| `cancelled` | Отменён пользователем |

Запуски `empty` не засоряют историю: `GET /tasks/{id}/runs` показывает их только с
`include_empty=true`. Пробный запуск `empty` не бывает.

Итог запуска (`result`): результат последнего шага и список созданных файлов, а если
запуск закончился раньше — причина.

## Журнал запуска

У каждого запуска один журнал (`run_log`, по `task_id` и `run_id`), записи только
добавляются. Его ведёт runner; executor своего журнала не ведёт и всё нужное
возвращает в ответе на вызов.

| Запись | Что в ней |
| --- | --- |
| `start` | Название, версия, откуда запуск, пробный ли, настройки задачи, посчитанные переменные |
| `step` | Ключ шага, команда, номер попытки, статус (`ok`, `error`, `skipped`), подставленные аргументы, результат (длинный обрезается до 20 000 символов), ошибка, traceback при сбое команды, длительность, строки, которые написала сама команда (`ctx.log`) |
| `notify` | Сообщение пользователю от шага |
| `end` | Статус, ошибка, итог |

Каждая попытка шага — отдельная запись. `GET /runs/{id}/log` отдаёт журнал целиком,
`GET /runs/{id}` — запуск с записями о шагах.

## Пробный запуск

Пробный запуск — это исполнение версии (можно черновой) прямо сейчас с флагом
`dry_run`. Его просит пользователь в чате (`task_dry_run`) или клиент через
`POST /runs {task_version_id, dry_run: true}`.

Executor передаёт флаг команде, а что он значит, решает сама команда (см.
[TOOLS.md](TOOLS.md#пробный-запуск)):

- команды, которые смотрят или считают, выполняются как обычно — без их данных
  пробный запуск бессмыслен;
- команды, которые что-то меняют, всё проверяют, как при настоящем вызове, но ничего не
  делают и пишут в журнал, что сделали бы: «Пробный запуск: переложил бы
  «Входящие/a.pdf» в «Счета/a.pdf»»;
- `mail.send` кладёт письмо в черновики, чтобы его можно было открыть и проверить;
- новые файлы создаются как обычно, но только в результатах запуска.

Ничего автоматически не чинится: результат с ошибками как есть уходит в чат.

## Уведомления

Команда может сообщить что-то пользователю — `ctx.notify()`, в задаче это шаг
`user.notify`. Сообщение:

1. записывается в журнал запуска (`notify`);
2. вне пробного запуска уходит через `POST main/internal/notify` в чат, из которого
   собрана задача, — как «Задача «название»: текст» (как агент показывает его модели —
   в [CHAT.md](CHAT.md#сообщения-задач)), и публикуется событием `notify`.

В пробном запуске сообщение остаётся только в журнале. Если у задачи нет чата или он
недоступен, сообщение остаётся в журнале и в событиях.

## Срок хранения

Раз в 6 часов и при старте каждый сервис чистит то, что пишет сам, старше
`RETENTION_DAYS` (15 дней):

- runner — законченные запуски вместе с журналом;
- executor — папки `data:outputs/<запуск или чат>/`, в которых ничего не менялось;
- main — события.
