# Настройки

Этот документ описывает настройки, которые пользователь меняет, пока агент работает:
откуда берётся значение, какие настройки есть и как их менять через API.

Настройки бывают двух видов:

- **Для запуска** — всё, что нужно сервису до того, как откроется база: адреса и
  порты, токены, `DATA_DIR`, хранилище паролей. Они задаются только переменными
  окружения и читаются один раз при старте. Список — в
  [DEPLOY.md](DEPLOY.md#переменные-окружения). Модели LLM подключаются отдельно —
  провайдерами (см. [LLM.md](LLM.md)), а их общие параметры — рабочие настройки ниже.
- **Рабочие** — описаны здесь. Они меняются через API main и применяются без
  перезапуска: сервисы читают значение при каждом использовании.

## Откуда берётся значение

Порядок такой:

1. **Переменная окружения** с тем же именем в верхнем регистре (`retention_days` →
   `RETENTION_DAYS`). Если она задана, настройка **закреплена**: API её не меняет и
   отвечает ошибкой. Так в Docker и при разработке значение фиксируется через `.env`.
   Пустая переменная считается незаданной.
2. **Таблица `settings`** — значение, сохранённое через API.
3. **Значение по умолчанию** из кода.

Неверное значение в переменной окружения останавливает сервис при старте. Сохранённое
в базе значение, которое перестало подходить (например, после обновления), пропускается
с предупреждением в логе, и используется значение по умолчанию.

Код — `common/tunables.py`. Писать в таблицу `settings` может только main.

## Список

| Настройка | Что задаёт | По умолчанию | Ограничения |
| --- | --- | --- | --- |
| `workspace_dir` | Рабочая папка: документы пользователя. Пути в задачах — от неё, команды не выходят за её пределы | `workspace` в корне проекта | через API — только полный путь |
| `retention_days` | Сколько дней хранятся законченные запуски с журналом, файлы в `data:outputs` (запусков и чатов) и события | `15` | не меньше 1 |
| `chat_idle_hours` | Через сколько часов без сообщений удаляется временный чат — тот, из которого не собрали и не правили задачу | `24` | не меньше 1 |
| `agent_max_iterations` | Сколько раз за один ход чата модель может вызвать команды | `16` | не меньше 1 |
| `agent_tools_top_k` | Сколько команд, ближайших к запросу, видит модель, если задана модель эмбеддингов | `24` | не меньше 1 |
| `agent_message_max_chars` | Сколько символов может быть в одном сообщении чата; длиннее — отказ `413` до сохранения (текст — файлом в рабочей папке) | `20000` | не меньше 100 |
| `agent_history_messages` | Сколько последних сообщений чата видит модель (текущий ход — всегда целиком) | `40` | не меньше 2 |
| `compiler_max_attempts` | Сколько попыток у компилятора собрать задачу, проходящую проверки | `3` | не меньше 1 |
| `tool_timeout_sec` | Сколько секунд может выполняться команда, если она не задала свой таймаут | `300` | не меньше 1 |
| `plugin_account_idle_min` | Через сколько минут без вызовов останавливается сервер плагина для аккаунта (следующий вызов запустит его снова) | `15` | не меньше 1 |
| `llm_timeout_sec` | Сколько секунд ждать ответа LLM | `300` | не меньше 1 |
| `llm_max_retries` | Сколько раз повторить запрос к LLM при сетевом сбое | `2` | не меньше 0 |
| `llm_no_proxy` | Ходить к LLM напрямую, не через прокси из `HTTP(S)_PROXY` | `true` | да или нет |
| `llm_<роль>_temperature` | Температура модели роли `chat` / `instruct`; пусто — как на сервере | пусто | от 0 до 2 или пусто |
| `llm_<роль>_top_p` | top_p модели роли; пусто — как на сервере | пусто | от 0 до 1 или пусто |
| `llm_<роль>_thinking` | Рассуждения модели роли (`chat_template_kwargs.enable_thinking`: Qwen3 и др. на vLLM, SGLang, llama.cpp); пусто — как на сервере | пусто | `on`, `off` или пусто |
| `llm_<роль>_reasoning_effort` | Глубина рассуждений модели роли для reasoning-моделей; пусто — не отправляется | пусто | `low`, `medium`, `high` или пусто |

Время ограничивают только `tool_timeout_sec` и `llm_timeout_sec`: запросы между
сервисами ждут столько, сколько идёт работа. Команды, которые сами спрашивают модель
(`docs.make_template`, `llm.*`), ждут её внутри себя, поэтому `tool_timeout_sec` для них
должен быть больше `llm_timeout_sec`.

Смена `workspace_dir` действует со следующего вызова команды. Пути в задачах
относительные, поэтому задачи продолжают работать в новой папке, если в ней та же
структура.

## API

| Маршрут | Что делает |
| --- | --- |
| `GET /settings` | Все настройки с текущими значениями |
| `PATCH /settings` | Изменить одну или несколько; `null` возвращает значение по умолчанию |

Ответ обоих маршрутов:

```json
{"settings": [
  {"key": "retention_days", "value": 30, "default": 15, "source": "db", "locked": false,
   "type": "int", "min": 1, "max": null, "choices": null, "description": "Сколько дней хранятся …"},
  {"key": "workspace_dir", "value": "/workspace", "default": "/app/workspace", "source": "env", "locked": true,
   "type": "dir", "min": null, "max": null, "choices": null, "description": "Рабочая папка: …"}
]}
```

- `source` — откуда значение: `env`, `db` или `default`;
- `locked` — задано переменной окружения, через API не меняется;
- `type` — `int`, `float` (дробное; у сэмплинга пустое — `null`), `bool`, `choice` (одно из `choices`) или `dir` (путь к папке).

`PATCH` принимает объект `{настройка: значение}` и меняет всё или ничего: если хотя бы
одно значение не подходит, не сохраняется ни одно, а ответ `400` перечисляет причины:

```bash
curl -X PATCH http://127.0.0.1:8000/settings -H "Authorization: Bearer $(cat data/api_token)" \
  -H 'Content-Type: application/json' \
  -d '{"retention_days": 30, "agent_tools_top_k": 0}'
```

```json
{"error": {"code": "BAD_REQUEST", "message": "Настройки не изменены",
           "details": {"agent_tools_top_k": "не меньше 1"}}}
```
