# Развёртывание

Этот документ описывает, как запустить агент локально и в Docker, и перечисляет все
переменные окружения.

Код один и тот же: шесть сервисов всегда работают отдельными процессами. Локально их
поднимает `launcher.py`, в Docker — compose, по контейнеру на сервис. Режима «всё в
одном процессе» нет.

## Локально (Windows, Linux, macOS)

Нужны Python 3.12+ и [uv](https://docs.astral.sh/uv/). Зависимости ставятся только в
`.venv` проекта:

```bash
uv sync --extra dev
```

```bash
cp .env.example .env
```

В `.env` укажите `LLM_BASE_URL` и `LLM_MODEL` — при старте они станут провайдером
`default` — или оставьте `LLM_*` пустыми и подключите модель после запуска через
`POST /llm/providers` (см. [LLM.md](LLM.md)). Рабочую папку с документами
пользователя задайте в `WORKSPACE_DIR` (на Windows, например,
`C:/Users/<имя>/Documents`) или потом через `PATCH /settings` (см.
[SETTINGS.md](SETTINGS.md)).
`launcher.py` читает `.env` из корня репозитория; переменные, уже заданные в оболочке,
главнее.

Демо-папка для сценария еженедельного отчёта — пример отчёта и выгрузки продаж за
прошлую, текущую и более старую неделю:

```bash
uv run python misc/make_demo_data.py workspace
```

Запуск:

```bash
uv run python launcher.py
```

`launcher.py`:

- запускает сначала `main`, ждёт его `/health` (до 30 секунд), потом остальные;
- раздаёт порты (ниже) и пишет адрес main в `DATA_DIR/runtime.json`;
- не запускается второй раз с той же папкой данных: второй экземпляр выполнял бы каждую
  задачу дважды. Он сообщает адрес уже работающего и выходит с кодом 1;
- собирает логи всех сервисов в одну консоль с префиксом `[сервис]`;
- перезапускает упавший сервис через 2 секунды, но не больше 5 раз в минуту;
- если `INTERNAL_TOKEN` не задан, создаёт его на время запуска — все сервисы его
  дочерние процессы и получают одинаковый.

Один сервис на переднем плане и перезапуск при правке кода:

```bash
uv run python launcher.py runner --reload
```

Так каждый сервис запускается своим `launcher.py`, и токен, созданный одним из них,
другие не знают: для этого режима задайте `INTERNAL_TOKEN` в `.env`. `--reload` следит за
папкой сервиса и `common/`; правки команд в `internal_tools/` требуют перезапуска
executor.

Порты:

- **main** слушает `MAIN_PORT`, если он задан. Иначе — порт, который был у него в
  прошлый раз, если тот свободен. Иначе — случайный свободный из 20000–32767: выше
  известных портов и ниже диапазонов, которые ОС раздаёт сама. Порт хранится в
  `DATA_DIR/runtime.json` и после остановки, поэтому у main он постоянный, пока его
  не займёт кто-то другой. Свободным считается порт, к которому удалось привязаться: на
  Windows Hyper-V резервирует целые диапазоны, и «свободный с виду» порт может отказать;
- **остальные сервисы** при каждом старте получают свободный порт от ОС и сообщают его
  main (`POST /internal/register`). Снаружи к ним не обращаются;
- launcher печатает адрес main при старте: `API at http://127.0.0.1:<порт>`.
  Документация API — `<адрес>/docs`.

`runtime.json`:

```json
{"main_url": "http://127.0.0.1:28077", "port": 28077, "pid": 41234}
```

`main_url` и `pid` — пока агент работает; после остановки остаются `null`, а `port`
остаётся для следующего запуска. Токенов в файле нет.

Одиночный сервис (`launcher.py runner`) слушает свой `PORT` или стандартный порт
8000–8005: так его запускает Docker.

Пароли аккаунтов и ключи провайдеров LLM локально хранятся в системном хранилище: Windows Credential Manager,
macOS Keychain или Secret Service в Linux (`KEYRING_BACKEND=system`). Если его нет
(сервер без графической сессии), используйте файл: `KEYRING_BACKEND=file` и
`KEYRING_PASSWORD`.

## Docker

```bash
cp deploy/.env.example deploy/.env
```

Отредактируйте `deploy/.env`:

- блок `DEPLOY SETTINGS`: порт и адрес публикации main (`AGENT_DEPLOY_PORT`,
  `AGENT_DEPLOY_HOST`), имя образа, префикс контейнеров и **папка пользователя**
  `AGENT_DEPLOY_WORKSPACE_PATH`, которая монтируется в `/workspace`;
- `TZ` — часовой пояс контейнеров: в нём срабатывает cron;
- настройки LLM;
- `INTERNAL_TOKEN` — обязателен, общий для всех контейнеров;
- `KEYRING_PASSWORD` — ключ к файлу паролей;
- `API_TOKEN` — если пусто, main создаст токен при первом старте: `docker exec <префикс>-main cat /data/api_token`;
- `AGENT_DEPLOY_ALLOWED_HOSTS` — имена, по которым клиенты обращаются к main; при публикации в сеть добавьте имя или адрес сервера.

```bash
docker compose -f deploy/docker-compose.yaml up -d --build
```

Устройство:

- **один образ** (`Dockerfile`: python:3.12-slim, пользователь без root, зависимости из
  `pyproject.toml`), по контейнеру на сервис — `command: python launcher.py <сервис>`;
- **наружу опубликован только main**; остальные в сети compose и стартуют после того,
  как main стал здоровым;
- отличия от локального запуска заданы в `environment` compose: `MAIN_URL=http://main:8000`,
  `SERVICE_HOST=0.0.0.0`, свой `SELF_URL` у каждого сервиса, `DATA_DIR=/data`,
  `WORKSPACE_DIR=/workspace` (поэтому рабочая папка в Docker закреплена и через API не
  меняется), `KEYRING_BACKEND=file`;
- **данные — в именованном томе `agent-data`**, а не в папке хоста: блокировки SQLite в
  режиме WAL ненадёжны на bind mount из Windows. Папка пользователя монтируется обычным
  bind mount.
- **обновление** — та же команда `up -d --build`: main при старте сам доводит базу до
  новой схемы, предварительно сохранив копию в `/data/backups` (см.
  [DATABASE.md](DATABASE.md#схема-и-миграции)), остальные контейнеры ждут его.

## Переменные окружения

Настройки для запуска читает `Settings.from_env()` (`common/settings.py`). Неверное
значение останавливает сервис при старте с понятной ошибкой, а не всплывает позже.
Обязательных переменных нет.

Рабочие настройки (рабочая папка, сроки хранения, параметры агента, таймауты команд и
LLM, прокси и `reasoning_effort` для LLM) меняются через API — см. [SETTINGS.md](SETTINGS.md). Их тоже можно задать переменной
окружения с тем же именем в верхнем регистре; тогда значение закреплено и через API не
меняется.

**Сервисы**

| Переменная | Значение | По умолчанию |
| --- | --- | --- |
| `MAIN_PORT` | Порт main при запуске всех сервисов; пусто — постоянный свободный (см. [порты](#локально-windows-linux-macos)) | не задано |
| `MAIN_URL` | Куда сервисы шлют запросы; при запуске всех сервисов launcher задаёт его сам | `http://127.0.0.1:8000` |
| `SERVICE_HOST` | На каком адресе слушать | `127.0.0.1` |
| `PORT` | Порт одиночного сервиса (`launcher.py <сервис>`, Docker); при запуске всех сервисов его раздаёт launcher | 8000–8005 по сервису |
| `SELF_URL` | Адрес, который сервис сообщает main | `http://127.0.0.1:<порт>` |
| `API_TOKEN` | Токен внешнего API (`Authorization: Bearer`), нужен всегда; пусто — main создаёт его в `DATA_DIR/api_token` | не задано |
| `ALLOWED_HOSTS` | Заголовки `Host`, на которые отвечает main (защита от DNS rebinding); `*` — без проверки | `127.0.0.1,localhost` |
| `ALLOWED_ORIGINS` | Источники для CORS через запятую | не задано |
| `INTERNAL_TOKEN` | Токен между сервисами (`X-Internal-Token`); пусто — без проверки, локально его создаёт `launcher.py` | не задано |
| `LOG_LEVEL` | Уровень логов | `INFO` |

**Папки**

| Переменная | Значение | По умолчанию |
| --- | --- | --- |
| `DATA_DIR` | `app.db`, `templates/`, `outputs/`, `secrets.enc`, `llm_keys.enc`, `backups/` | `data` |

**LLM** — модели, которые при старте станут провайдерами. Таймаут, повторы, прокси и
`reasoning_effort` — рабочие настройки `LLM_TIMEOUT_SEC`, `LLM_MAX_RETRIES`,
`LLM_NO_PROXY`, `LLM_CHAT_REASONING_EFFORT` (см. [SETTINGS.md](SETTINGS.md)).

| Переменная | Значение | По умолчанию |
| --- | --- | --- |
| `LLM_BASE_URL` | OpenAI-совместимый `/v1` с вызовом инструментов | `http://127.0.0.1:11434/v1` |
| `LLM_API_KEY` | Ключ; пусто — без заголовка `Authorization` | не задано |
| `LLM_MODEL` | Модель на всё. Задана — при старте main модели из `LLM_*` становятся провайдерами `default…` и занимают пустые роли (см. [LLM.md](LLM.md#модели-из-переменных-окружения)); пусто — остальные `LLM_*` не читаются | не задано |
| `LLM_MODEL_CHAT` | Агент в чате и сборка задач | `LLM_MODEL` |
| `LLM_MODEL_INSTRUCT` | Команды `llm.*` и разметка шаблонов | `LLM_MODEL` |
| `LLM_MODEL_EMBED` | Модель эмбеддингов для отбора команд; пусто — агент видит все | не задано |
| `LLM_EMBED_BASE_URL` | Отдельный сервер эмбеддингов | `LLM_BASE_URL` |
| `LLM_EMBED_API_KEY` | Ключ сервера эмбеддингов. Пусто — на том же сервере берётся `LLM_API_KEY`, отдельному серверу ключ основного не передаётся | не задано |

**Секреты**

| Переменная | Значение | По умолчанию |
| --- | --- | --- |
| `KEYRING_BACKEND` | `system` — системное хранилище, `file` — файлы `DATA_DIR/secrets.enc` (пароли аккаунтов) и `DATA_DIR/llm_keys.enc` (ключи провайдеров LLM) | `system` |
| `KEYRING_PASSWORD` | Ключ к этим файлам; обязателен для `file` | не задано |

**Только Docker** (`deploy/.env`)

| Переменная | Значение | По умолчанию |
| --- | --- | --- |
| `AGENT_DEPLOY_PORT` | Порт main на хосте | `8000` |
| `AGENT_DEPLOY_HOST` | Адрес публикации main; `0.0.0.0` — в сеть | `127.0.0.1` |
| `AGENT_DEPLOY_ALLOWED_HOSTS` | `ALLOWED_HOSTS` для main; `main` добавляется сам | `127.0.0.1,localhost` |
| `AGENT_DEPLOY_IMAGE` | Имя образа | `fintech2026-agent:0.1.0` |
| `AGENT_DEPLOY_CONTAINER_PREFIX` | Префикс имён контейнеров | `fintech2026` |
| `AGENT_DEPLOY_WORKSPACE_PATH` | Папка пользователя на хосте → `/workspace` | не задано |
| `TZ` | Часовой пояс контейнеров; в нём срабатывает cron | `Europe/Moscow` |

## Проверка

```bash
uv run pytest
```

Живость сервиса — `GET /health` у каждого; какие сервисы main знает и когда видел их
последний раз — `GET /services`.
