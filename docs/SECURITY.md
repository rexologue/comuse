# Безопасность

Этот документ описывает, от чего агент защищён и как: права задач, вопросы в чате,
песочницы, токены и хранение паролей.

Главное: все проверки делает код, а не модель. При запуске задачи модель не решает, что
делать, — шаги и их аргументы одобрил пользователь. В чате модель предлагает
действия, но всё, что что-то меняет, ждёт ответа пользователя.

## Риски и меры

| Риск | Мера |
| --- | --- |
| Задача делает не то, что одобрено | Права задачи — это её одобренные шаги с аргументами; отдельного списка прав нет. Любая правка — новая версия, активной она становится только после одобрения пользователем |
| Агент сам включил задачу | Не может: инструмента для одобрения у агента нет, отвечать на одобрения он не умеет |
| Модель в чате сделала действие без согласия | Команда, которая что-то меняет (`confirm` не `False`), в чате не выполняется до ответа пользователя. Подтверждение засчитывается, только если после вопроса появилось сообщение пользователя: в том же ходе модель подтвердить не может |
| Prompt injection из письма или документа | Прочитанный текст не может подтвердить действие (см. выше). В задаче данные отбирает команда поиска: `mail.search` с `sender_in: ["*@company.ru"]` не отдаст письмо `attacker@evil.com` |
| Письмо с подделанным From | `sender_in` отбирает по заголовку From и подлинность не проверяет. Ответ уйдёт на этот адрес — в разрешённый домен, а не подделавшему; другие действия с письмом задача выполнит |
| Письмо ушло не тому | Адресаты — одобренные аргументы шага или отобранные `sender_in`. По умолчанию задача кладёт письма в черновики, отправляет их человек; разрешить отправку сразу (`mail.send_directly`) может только он сам. В чате `mail.send` спрашивает перед каждым письмом |
| Пробный запуск сделал что-то по-настоящему | Команда, о которой чат спрашивает, сама проверяет `ctx.dry_run` и только пишет, что сделала бы. Тест по всему каталогу не пропустит команду, которая этого не делает |
| Доступ к файлам вне папки пользователя | Аргументы-пути executor проверяет до вызова: только рабочая папка и `data:templates` / `data:outputs`; `..`, симлинки наружу и абсолютные пути вне рабочей папки отклоняются, база и файл паролей недоступны |
| Шаблон в задаче выполняет произвольный код | Шаблоны Jinja исполняются в `SandboxedEnvironment` со `StrictUndefined` |
| Пароль утёк в лог, промпт или git | Пароли только в хранилище секретов (ниже). Команды получают аккаунт по имени, поэтому ни аргументы, ни журнал запуска, ни модель пароля не видят |
| Чужой процесс дёргает API | Наружу открыт только main. Внешний API закрывается `API_TOKEN`, внутренние маршруты — `INTERNAL_TOKEN` |

## Вопросы в чате

Подробно — в [CHAT.md](CHAT.md#вопрос-перед-действием). Коротко:

- спрашивают все команды, кроме объявивших себя безвредными (`confirm=False`): они
  только смотрят или считают и создают файлы только в результатах запуска;
- ответ должен быть сообщением пользователя после вопроса;
- «да, и больше не спрашивай» снимает вопрос для одной команды в одном чате до
  перезапуска agent-loop; `mail.send` спрашивает всегда.

## Токены

| Токен | Где | Что закрывает |
| --- | --- | --- |
| `API_TOKEN` | `Authorization: Bearer …` | Внешний API main. Пусто — без проверки; так можно только при публикации на `127.0.0.1` |
| `INTERNAL_TOKEN` | `X-Internal-Token: …` | Маршруты сервисов и внутренние маршруты main. Локально `launcher.py` создаёт его на каждый запуск; в Docker задаётся в `deploy/.env` |

Учётные данные клиента main дальше сервисов не передаёт: сервисам он предъявляет
внутренний токен.

## Секреты

Секретов два вида, и хранятся они раздельно, у каждого хранилища один сервис, который
в него пишет (`common/secrets.py`):

| Хранилище | Что | Пишет | Читает | Служба в системном хранилище | Файл |
| --- | --- | --- | --- | --- | --- |
| пароли аккаунтов | почта и другие аккаунты команд | executor | executor, в момент вызова команды, которая объявила аргумент аккаунта в `secrets` | `fintech2026`, ключ `account:<имя>` | `secrets.enc` |
| ключи LLM | ключи провайдеров из `/llm/providers` | main | agent-loop, compiler, executor — когда строят клиент провайдера | `fintech2026-llm`, ключ — id провайдера | `llm_keys.enc` |

- `KEYRING_BACKEND=system` — системное хранилище: Windows Credential Manager, macOS
  Keychain, Secret Service.
- `KEYRING_BACKEND=file` — файлы в `DATA_DIR`, зашифрованные Fernet ключом из
  `KEYRING_PASSWORD` (scrypt, новая соль при каждой записи). Так работает Docker.
- В базе у аккаунта только `secret_ref` — ключ записи, у провайдера — признак
  `has_key`. Ни `GET /accounts`, ни `GET /llm` секретов не отдают.

Ключ LLM из окружения (`LLM_API_KEY`, `LLM_EMBED_API_KEY`) читает только клиент LLM.
Настоящие значения — только в `.env` и `deploy/.env`, которые в git не попадают;
шаблоны `.env.example` содержат лишь заглушки.
