# Свои команды

Кроме встроенных команд из `internal_tools/` у агента бывают свои: их добавляет
пользователь (свой скрипт) или пишет чат. Это команды `ext.<имя>`. В каталоге (`GET
/tools`) они стоят рядом со встроенными с `"source": "external"` и номером версии, и
агент с компилятором пользуются ими так же. Код — `common/external_tools/`, API и
таблицы — у executor.

## Версия команды

Каждая версия — отдельная папка:

```
DATA_DIR/external_tools/<имя>/<версия>/
  tool.json           манифест
  main.py             def run(args, ctx)
  …                   другие .py и небольшие файлы данных (.json, .txt, .csv, .md, .yaml)
  requirements.txt    пакеты, которые команда объявила
  requirements.lock   точные версии всех пакетов с хешами
  .venv/              своё окружение версии
```

Имя — латиница в нижнем регистре, цифры и `_` (`parse_invoice`). Версии нумеруются
1, 2, 3… Хеш версии считается по всем файлам, кроме `.venv`, и хранится в базе.

### tool.json

```json
{
  "title": "Разобрать дату",
  "description": "Переводит дату в свободной форме в ISO 8601",
  "card": "Разобрать дату «{text}»",
  "confirm": false,
  "timeout": 60,
  "input_schema": {"type": "object", "properties": {"text": {"type": "string"}}, "required": ["text"]},
  "output_schema": {"type": "object", "properties": {"iso": {"type": "string"}}, "required": ["iso"]}
}
```

| Поле | Что это |
| --- | --- |
| `title`, `description` | Название и описание: по описанию модель выбирает команду |
| `card` | Что видит пользователь перед вызовом, с `{аргумент}`; пусто — `title` |
| `confirm` | Как у встроенных: `true` — спросить, `"always"` — каждый раз, `false` — не спрашивать |
| `timeout` | Секунды; пусто — `tool_timeout_sec` |
| `input_schema`, `output_schema` | JSON Schema объекта. Аргумент с `"x-path": "path"` (у списка — в `items`) — путь в рабочей папке: executor проверяет его до вызова и передаёт команде полным путём |

### main.py

```python
from agent_tool import ToolError   # необязательно: ошибка для пользователя без traceback


def run(args, ctx):
    ...
    out = ctx.output_path("итог.txt")    # файл в результатах запуска, станет артефактом
    ctx.log("строк: 3")                  # строка в журнал запуска или трассу чата
    return {"iso": "...", "file": str(out)}
```

`ctx`: `mode` (`chat` / `run`), `dry_run`, `output_dir`, `log(text)`,
`output_path(filename)`. Ответ — JSON-объект по `output_schema`; полные пути в нём
executor переводит обратно в пути вида `Отчёты/x.xlsx` / `data:outputs/…`. Что команда
печатает, попадает в журнал и ответ не ломает.

Аккаунтов и LLM у своих команд нет: это детерминированные функции. Модель, почта —
соседние шаги `llm.*`, `mail.*` в задаче.

## Пакеты

Пакеты ставит uv (зависимость проекта, поэтому он есть везде, где стоит агент):

1. при сохранении черновика `requirements.txt` разрешается в `requirements.lock`:
   точные версии всех пакетов, включая транзитивные, с хешами. Этот список видит тот,
   кто одобряет версию;
2. при одобрении (или первом вызове, если `.venv` пропал) — `uv venv` на интерпретаторе
   агента и `uv pip sync --require-hashes --only-binary :all:`.

Ставятся только готовые wheel-пакеты: при установке wheel код пакета не выполняется, при
сборке из исходников выполнялся бы. Пакета без wheel под эту платформу не поставить —
ошибка это скажет. Кеш uv — `DATA_DIR/cache/uv`: одинаковые пакеты в разных версиях
ставятся почти мгновенно и почти не занимают места. Индекс пакетов — PyPI или зеркало из
`UV_INDEX_URL`; без сети работают только команды без пакетов.

Наших библиотек в `.venv` команды нет: что ей нужно, она объявляет сама.

## Жизнь версии

```
черновик ──одобрил человек──▶ одобрена, текущая ──одобрили новую──▶ одобрена, не текущая
   │                                                                        │
   └──выбросили──▶ удалена                       ни одна задача не держит ──┴──▶ удалена
```

- **Черновик** у команды один. Его можно сохранять сколько угодно раз: номер не растёт,
  папка переписывается (`.venv` переиспользуется). При каждом сохранении проверяются
  имя, манифест, файлы (только внутри папки, разрешённые расширения, размер), что `.py`
  компилируется и что пакеты разрешаются. Все несовпадения — одной ошибкой, и тогда
  ничего не записано.
- **Одобряет только человек**, прочитав код и список пакетов. Если файлы черновика
  изменились после сохранения, одобрение отклоняется. После одобрения ставятся пакеты,
  версия становится текущей, каталог executor обновляется (agent-loop видит новую
  команду в течение минуты).
- **Одобренная версия не меняется.** Перед каждым вызовом executor сверяет файлы с
  хешем; не совпало — команда не запускается.

## Версия в задаче

Шаг задачи со своей командой хранит её версию: `{"tool": "ext.parse_date",
"tool_version": 2, …}`. Модель версию не выбирает — её ставит компилятор:

- **новая задача** — текущая версия;
- **правка словами** — та, что у задачи уже была (что бы модель ни написала); новой для
  задачи команде — текущая;
- **правка вручную** (`POST /tasks/{id}/versions`) — указанная в шаге, иначе как было.

У одной задачи у команды одна версия. Задача проверяется по схемам своей версии:
аргумент, который появился только в новой версии, задаче на старой не подходит.

Runner передаёт версию в executor, и тот запускает ровно её (ей нужен свой `.venv`,
он создаётся при первом вызове). Чат всегда вызывает текущую версию.

**Переход на новую версию** — только явно. Когда одобрена новая версия, задачи остаются
на своей; в панели задачи видно «у команды есть v3» (`tool_updates` в `GET /tasks/{id}`)
и кнопка «Перевести». Она вызывает `POST /tasks/{id}/tool-versions`: черновик задачи, где
все шаги команды на новой версии, с diff («версия команды v2 → v3») и одобрением — как
любая правка, с пробным запуском до одобрения. Если шаги не подходят к схемам новой
версии, черновик не создаётся, а ответ называет, что не сходится: такую задачу правят
словами.

**Старые версии** executor удаляет сам (папку и строку), когда версия не текущая и её не
закрепляет ни черновик, ни активная версия неархивной задачи, ни версия задачи с идущим
запуском.

## Вызов

Версия работает в отдельном процессе: python из её `.venv` запускает
`common/external_tools/shim.py`, тот получает `{"args", "context"}` на stdin, вызывает
`run` и отвечает JSON на stdout. Процесс получает очищенное окружение (без токенов,
ключей и прокси агента), флаги `-I -B -X utf8` и рабочую папку результатов; по
тайм-ауту его убивают. Ответ проверяется по `output_schema`.

Это не песочница: код может прочитать то, что может пользователь, и выйти в сеть.
Безопасной команду делает человек, который прочитал и одобрил её версию.

## API

Через main, с токеном внешнего API.

| Маршрут | Что делает |
| --- | --- |
| `GET /external-tools` | Команды: текущая версия, черновик, все версии |
| `GET /external-tools/{name}/versions/{version}` | Версия: манифест, пакеты, хеш, файлы |
| `PUT /external-tools/{name}/draft` | Сохранить черновик: `{"manifest", "files", "requirements"}` |
| `DELETE /external-tools/{name}/draft` | Выбросить черновик |
| `POST /external-tools/{name}/versions/{version}/approve` | Одобрить черновик |

```json
{
  "manifest": {"title": "Разобрать дату", "description": "…", "input_schema": {…}, "output_schema": {…}},
  "files": {"main.py": "from dateutil import parser\n\ndef run(args, ctx):\n    …"},
  "requirements": ["python-dateutil>=2.8"]
}
```

Ошибки проверки и установки — `400` с текстом, что не так.
