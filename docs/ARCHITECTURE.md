# Архитектура

Этот документ описывает, из чего состоит агент и как части связаны между собой.

Агент — шесть FastAPI-сервисов. Клиент и сервисы общаются только через `main`, по
HTTP; отдельного сервиса хранилища нет, все пишут в один файл SQLite через общий пакет
`common/storage`. Локально сервисы по умолчанию работают в одном процессе на одном
порту (`single_app.py`: main в корне, остальные под `/svc/<сервис>`), с
`RUN_MODE=multi` — каждый в своём, в Docker — по контейнеру. Связи между ними от этого
не меняются (см. [DEPLOY.md](DEPLOY.md)).

```text
                 Клиент: UI, curl или OpenAI-клиент
                                │
                 ┌──────────────▼───────────────┐
                 │          main :8000          │
                 │ шлюз · реестр · оркестрация  │
                 │ уведомления · события (SSE)  │
                 └──────────────┬───────────────┘
                                │  вызовы между сервисами тоже через main
   ┌─────────────┬──────────────┼──────────────┬──────────────┐
   ▼             ▼              ▼              ▼              ▼
agent-loop    compiler        runner        executor      scheduler
  :8001         :8002          :8003          :8004          :8005
  чат        чат → задача   исполняет      команды,          cron
                             задачу        пути, секреты
   │             │                             │
   ▼             ▼                             ▼
     LLM-провайдер (OpenAI API)  ◀──── internal_tools/ (только llm.*)

        SQLite · data/app.db · у каждой таблицы один сервис-владелец
```

## Каждая часть знает только своё

Главное правило устройства: логика одной части не проникает в другие.

| Часть | Знает | Не знает |
| --- | --- | --- |
| scheduler | **когда** запускать задачу (cron) | что делают её шаги; почту и папки не читает |
| runner | **в каком порядке** идут шаги, что делать при ошибке или пустом результате | что значит команда и её аргументы |
| executor | **чем** выполнить вызов: проверить аргументы по схеме, аргументы-пути по песочнице, достать объявленные секреты | что можно задаче, когда спрашивать человека, что значит пробный запуск |
| agent-loop | когда **спросить пользователя** перед командой | как выполняются команды |
| compiler | как **собрать и проверить** задачу | как её запускать: ничего не запускает |
| группа команд | всё о своей области: почта, файлы, отчёты. Свои настройки для задач, вид аккаунта, инструкции для агента и компилятора, поведение в пробном запуске | ничего за пределами своей области |

Отсюда несколько следствий, которые встречаются по всей документации:

- **Права задачи — это её одобренные шаги.** Отдельного списка прав нет. Команды
  простые (`mail.send` отправляет тем, кому сказали), а отбор того, с чем задача
  работает, делает команда, которая ищет: `mail.search` с `sender_in: ["*@company.ru"]`
  отдаёт только письма с этих адресов.
- **Одно одобрение — задачи целиком.** Запуск на шагах не останавливается и никого не
  ждёт. Как ведёт себя внешнее действие (письмо в черновики или сразу), решает
  команда по настройкам своей группы, которые меняет только пользователь.
- **Триггер — только время.** «Ответить на новые письма» — это задача по cron с шагом
  `mail.search`, а не особый триггер почты в scheduler.

## Сервисы

Порты в таблице — стандартные: их слушают сервисы в Docker и одиночный сервис. При
запуске всех сервисов локально main слушает свой постоянный порт, а остальные — тот же
порт под `/svc/<сервис>` (`single`) или любые свободные (`multi`).

| Сервис | Порт | Что делает | Пишет в таблицы |
| --- | --- | --- | --- |
| `main` | 8000 | Единственная точка входа: внешний API, реестр сервисов, прокси к ним, оркестрация версий задач, уведомления запусков в чат, поток событий, рабочие настройки, провайдеры LLM, миграции базы | `events`, `settings`, `llm_providers` |
| `agent_loop` | 8001 | Чат в формате OpenAI: история, отбор команд, вызовы LLM, вопросы перед действиями, мета-инструменты | `chat_sessions`, `chat_messages`, `trace_events` |
| `compiler` | 8002 | Чат → задача, проверки по каталогу, правки словами (LLM) и вручную, статусы задач, настройки задач | `tasks`, `task_versions` |
| `runner` | 8003 | Исполнение версии задачи по шагам, журнал запуска, отмена | `runs`, `run_log` |
| `executor` | 8004 | Выполнение одной команды, каталог команд, свои команды, аккаунты и их пароли | `accounts`, `external_tools` |
| `scheduler` | 8005 | Задания cron по активным задачам | — (задания только в памяти) |

Подробно о каждом — в отдельных справочниках: чат — [CHAT.md](CHAT.md), сборка и
правка задач — [TASKS.md](TASKS.md), scheduler и runner — [RUNS.md](RUNS.md),
executor и команды — [TOOLS.md](TOOLS.md), модели — [LLM.md](LLM.md), таблицы —
[DATABASE.md](DATABASE.md).

## Связь через main

- **Реестр.** Каждый сервис при старте и затем раз в 10 секунд шлёт
  `POST /internal/register {name, url}`. Так перезапущенный main снова узнаёт адреса,
  а сервисам нужен только `MAIN_URL`. Порты не зашиты: локально launcher раздаёт
  свободные (см. [DEPLOY.md](DEPLOY.md#локально-windows-linux-macos)). Адресов main
  не угадывает: пока сервис не зарегистрировался, обращение к нему получает `503`.
- **Прокси.** Клиентские запросы к чату, каталогу команд и аккаунтам main передаёт
  нужному сервису как есть, включая стриминг. Внутренние маршруты (`/executor/*`,
  `/runner/*`, `/scheduler/*`) доступны только с внутренним токеном: так agent-loop и
  runner зовут executor, scheduler — runner.
- **Оркестрация.** Действия, в которых участвуют несколько сервисов, живут в
  `main/orchestrator.py`: собрать черновик и объявить его (`task.draft`), одобрить версию
  и перезагрузить расписание, доставить уведомление запуска в чат задачи. Поэтому
  компилятор снаружи доступен только через маршруты main, а не общим прокси: одобрение
  в обход оркестратора не обновило бы расписание.
- **События.** Сервисы шлют события в `POST /internal/events`, main сохраняет их и
  раздаёт подписчикам `GET /events` (SSE). Типы событий — в [API.md](API.md#события).

## Путь работы

1. **Чат.** Клиент шлёт сообщение в `POST /agent/v1/chat/completions`. agent-loop
   вызывает LLM, та вызывает команды; каждый вызов идёт в executor через
   `POST main/executor/execute` с `mode: chat`. Команды, которые что-то меняют, ждут
   ответа пользователя.
2. **Сборка.** «Формируй задачу» → мета-инструмент `task_compile` → main →
   compiler: собирает задачу из разговора, проверяет, сохраняет черновик версии — он и
   ждёт одобрения. Ничего не запускается.
3. **Решение пользователя.** Пробный запуск (`task_dry_run`), правка словами
   (`task_patch`) или вручную (`POST /tasks/{id}/versions`), одобрение — только им
   самим через `POST /tasks/{id}/versions/{v}/approve`. После одобрения main просит scheduler
   перечитать задачу.
4. **Запуски.** scheduler по cron зовёт `POST main/runner/runs`; runner исполняет шаги
   через executor с `mode: run` и настройками задачи, пишет журнал и пересылает
   сообщения пользователю в чат, где задача собиралась. Команды, которые изменились после
   одобрения, задача не вызывает: запуск не начинается, задача ждёт решения пользователя.

## Код

```text
main/
  main.py            приложение и фоновая чистка событий
  orchestrator.py    compile/patch/edit → task.draft, approve → reload, уведомления
  registry.py        адреса сервисов
  proxy.py           потоковый прокси к сервисам
  events.py          шина событий: таблица events и подписчики SSE
  views.py           чтение задач и запусков для API
  auth.py            токен внешнего API
  api/               gateway (чат, каталог, аккаунты), tasks, approvals (черновики и события), settings, llm, logs, internal
agent_loop/
  loop.py            ход чата: LLM, команды, вопросы, подтверждения
  history.py         сессии, сообщения, трейс; окно истории для модели; поиск чата по переписке
  catalog.py         отбор команд по эмбеддингам
  meta_tools.py      инструменты управления задачами
  prompts.py         системный промпт
  api/chat.py        /v1/chat/completions, /sessions
compiler/
  compile.py         сборка из чата, правка словами и вручную, проверки по чату
  validate.py        проверки задачи по каталогу
  task_settings.py   настройки команд у задачи: для всей задачи и по шагам
  cards.py           карточки шагов, расписание словами, diff версий
  store.py           задачи и версии
  prompts.py         правила сборки
runner/
  engine.py          исполнение задачи и журнал
  retention.py       удаление старых запусков
  api/runs.py        запуск и отмена
executor/
  runtime.py         конвейер вызова команды
  paths.py           песочница путей
  outputs.py         удаление старых файлов результатов
  registry.py        каталог команд: internal_tools/ и свои команды
  api/               execute и каталог, external-tools, accounts
scheduler/
  jobs.py            задания cron
common/
  settings.py        настройки для запуска: из окружения
  tunables.py        рабочие настройки: окружение → таблица settings → по умолчанию
  llm.py             роли моделей: какой провайдер и модель отвечают сейчас
  secrets.py         хранилища секретов: пароли аккаунтов и ключи LLM
  service.py         каркас сервиса: логи в консоль и файл, БД, регистрация, токен, /health
  templating.py      шаблоны задач: Jinja-песочница и фильтры дат
  external_tools/    свои команды: манифест, одобренный код и черновик, пакеты (uv), запуск в отдельном процессе
  retention.py       общий цикл чистки по сроку хранения
  clients/           клиент LLM, клиент main
  schemas/           задача, формат вызова команды
  storage/           движок SQLite, модели, общие запросы, миграции
  tools/             каркас команд: @tool, контекст, определение и его хеш, настройки команд, виды аккаунтов, инструкции
internal_tools/      команды по группам (docs/reader.py — текст из docx, xlsx, pdf, txt)
web/                 веб-интерфейс, клиент API main (docs/WEB.md)
launcher.py          запуск: все сервисы в одном процессе или по процессу на сервис
single_app.py        все сервисы в одном приложении: main в корне, остальные под /svc/<сервис>
```
