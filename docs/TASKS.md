# Задачи

Этот документ описывает задачу: её формат, передачу данных между шагами, как
компилятор собирает её из чата и проверяет, как её правят, одобряют и настраивают.

Задача — замороженный сценарий: последовательность конкретных команд с аргументами.
При запуске ничего не планируется заново; LLM работает только внутри шагов `llm.*`,
если они есть. Задача и её версии хранятся отдельно: `tasks` — имя, статус, ссылка на
активную версию и настройки, `task_versions` — неизменяемые снимки сценария (см.
[DATABASE.md](DATABASE.md)). Любая правка — новая версия.

## Формат

Схема — `common/schemas/task.py` (pydantic); её же компилятор отдаёт модели как
JSON-схему.

```json
{
  "schema_version": 1,
  "title": "Еженедельный отчёт по продажам",
  "trigger": {"type": "cron", "expr": "0 10 * * MON"},
  "variables": {
    "week_start": "{{ today | start_of_prev_week }}",
    "week_end": "{{ today | end_of_prev_week }}"
  },
  "steps": [
    {"id": "sales_files", "tool": "fs.list",
     "args": {"folder": "Отчёты/Продажи", "pattern": "*.xlsx",
              "modified_from": "{{ week_start }}", "modified_to": "{{ week_end }}"},
     "on_empty": "skip"},
    {"id": "totals", "tool": "xlsx.aggregate",
     "args": {"inputs": "{{ sales_files.output.files }}", "sum_columns": ["Сумма, руб."],
              "group_by": "Клиент", "top_n": 5}},
    {"id": "top_clients", "tool": "data.map_rows",
     "args": {"rows": "{{ totals.output.groups }}",
              "fields": {"client": "row.key", "amount": "row.sums['Сумма, руб.'] | format_number"}}},
    {"id": "report", "tool": "docs.fill_template",
     "args": {"template": "data:templates/weekly_sales.docx",
              "context": {"revenue": "{{ totals.output.totals['Сумма, руб.'] | format_number }} руб.",
                          "top_clients": "{{ top_clients.output.rows }}"},
              "output_name": "Отчёт {{ week_start | format_date('%d.%m.%Y') }}.docx"}},
    {"id": "send_report", "tool": "mail.send",
     "args": {"account": "work_mail", "to": ["boss@company.ru"],
              "subject": "Отчёт по продажам за неделю", "body": "Отчёт во вложении.",
              "attachments": ["{{ report.output.path }}"]}}
  ]
}
```

| Поле | Что это |
| --- | --- |
| `schema_version` | Версия формата, сейчас `1` |
| `title`, `description` | Название и описание задачи |
| `trigger` | `{"type": "cron", "expr": "0 10 * * MON"}` (cron из 5 полей; дни недели только именами `MON`..`SUN`, см. [RUNS.md](RUNS.md#расписание)) или `{"type": "manual"}`. Только время запуска |
| `variables` | Значения, которые считаются один раз в начале запуска (даты, имена). Могут ссылаться на `today`, `now` и переменные выше |
| `steps` | Шаги по порядку |

Шаг:

| Поле | Что это | По умолчанию |
| --- | --- | --- |
| `id` | Имя шага, латиница: `[a-z][a-z0-9_]{0,40}`; уникально во всей задаче | — |
| `title` | Подпись карточки шага вместо собранной из шаблона команды | — |
| `tool`, `args` | Команда из каталога и её аргументы | — |
| `when` | Условие: выражение; ложно — шаг пропускается (`skipped`) | — |
| `foreach`, `as`, `steps` | Повторить вложенные шаги для каждого элемента списка; элемент доступен под именем `as` | `as`: `item` |
| `on_error` | `fail` — запуск падает; `retry` — повторить до `retries` раз (не после тайм-аута); `skip` — шаг пропущен, запуск идёт дальше (у `foreach` — пропущен элемент, на котором упало). У `foreach` нет `retry` | `fail` |
| `retries` | Повторы для `retry`, от 0 до 5 | `0` |
| `on_empty` | Пустой результат: `continue`; `fail` — запуск падает; `skip` — делать нечего, запуск тихо заканчивается | `continue` |

У шага есть либо `tool`, либо `foreach` со `steps`. Пустой результат — `null`, пустая
строка, список или объект, а также объект, у которого все поля пустые
(`{"files": []}`).

Настроек команд (`send_directly` и т. п.) в сценарии нет: они хранятся в задаче
отдельно, модель их не видит и не задаёт (см. [Настройки](#настройки)).

## Данные между шагами

Команды друг о друге не знают: данные между ними передаёт runner через шаблоны Jinja
в аргументах (`common/templating.py`, общий для компилятора и runner).

- Результат шага кладётся в контекст под его `id`: `{{ totals.output.groups }}`.
  Какие у результата поля, описывает output-схема команды (`GET /tools`).
- Перед шагом все строки его `args` рендерятся. Строка, которая целиком состоит из
  одного `{{ … }}`, подставляется как значение: список остаётся списком, число —
  числом. Любая другая строка рендерится в текст: `"Отчёт за {{ week_start }}"`.
- В `foreach` текущий элемент лежит под именем `as`, а результат всего шага —
  `<id>.output`, список по одному на элемент: `{<as>: элемент, <id шага>: его результат}`.
  Результат вложенного шага лежит прямо под его `id`, без `.output`:
  `{% for r in sort.output %}{{ r.file.path }} → {{ r.move.path }}{% endfor %}`. Компилятор
  отклоняет `{% for r in sort %}` (без `.output`) и `r.move.output.path` — они прошли бы
  остальные проверки и упали бы на запуске.
- Файлы передаются ссылками, а не содержимым: путь, список путей или результат
  `fs.list` целиком (`{{ sales_files.output.files }}`). Шаг модели (`llm.*`) получает
  текст: документ читает шаг перед ним (`docs.read`), а дальше идёт его `.output.text`.

```json
{"id": "sort", "foreach": "{{ files.output.files }}", "as": "file", "steps": [
  {"id": "doc", "tool": "docs.read", "args": {"path": "{{ file.path }}"}},
  {"id": "kind", "tool": "llm.classify",
   "args": {"input": "{{ doc.output.text }}", "labels": ["договор", "счёт", "акт"]}},
  {"id": "move", "tool": "fs.move",
   "args": {"src": "{{ file.path }}", "dst": "Документы/{{ kind.output.label }}/"}}
]}
```

В шаблонах доступны `today`, `now`, переменные задачи, результаты шагов выше и
переменная `foreach`. Шаблоны исполняются в песочнице Jinja с `StrictUndefined`:
ссылка на несуществующее имя — ошибка шага, а не пустая строка.

Фильтры, кроме стандартных Jinja (`length`, `default`, `join`…):

| Фильтр | Что делает |
| --- | --- |
| `start_of_week`, `end_of_week` | Понедельник и воскресенье недели даты |
| `start_of_prev_week`, `end_of_prev_week` | Границы прошлой недели |
| `start_of_month`, `end_of_month` | Границы месяца даты |
| `start_of_prev_month`, `end_of_prev_month` | Границы прошлого месяца |
| `add_days(n)` | Дата плюс `n` дней |
| `format_date('%d.%m.%Y')` | Дата строкой; по умолчанию ДД.ММ.ГГГГ. Для `now` время сохраняется: `now \| format_date('%Y-%m-%dT%H-%M-%S')` |
| `format_number(decimals=0)` | Число с пробелами между разрядами: `1 435 500` |

## Сборка из чата

Агент вызывает `task_compile` (см. [CHAT.md](CHAT.md#мета-инструменты)) →
`POST main/compiler/compile {session_id, title?, hint?}`.

1. Компилятор читает чат: сообщения пользователя и ассистента и каждый вызов команды с
   аргументами и результатом. Сообщения задач (`notice`) и мета-инструменты в эту
   расшифровку не входят.
2. Модель `LLM_MODEL_CHAT` получает правила сборки, инструкции всех групп команд для
   компилятора (см. [TOOLS.md](TOOLS.md#инструкции-группы)), каталог с аргументами и
   полями результатов, схему задачи, расшифровку и пожелания из `hint`.
3. Ответ проверяется (ниже). Ошибки уходят модели обратно с объяснением, до
   [`compiler_max_attempts`](SETTINGS.md) (3) попыток.
4. Задача сохраняется: статус `draft`, версия 1 в статусе `draft`, ссылка на чат,
   настройки команд со значениями по умолчанию. Черновик ждёт одобрения.

**Ничего не запускается.** Черновик с карточками шагов, расписанием словами и
настройками уходит в чат; дальше решает пользователь (см. «Одобрение»).

Правила сборки, коротко: повторить успешную последовательность действий из разговора
и выбросить неудачные попытки и разведку; не добавлять действий, которых не было;
обобщить конкретику (даты — переменными и фильтрами, конкретные файлы и письма —
шагами, которые найдут их при запуске); задача никого ни о чём не спрашивает; тексты,
которые пользователь написал сам, переносить дословно.

## Проверки

По каталогу (`compiler/validate.py`; так же проверяется и ручная правка):

- схема задачи; cron разбирается, дни недели в нём — именами, а не числами;
- команда есть в каталоге, аргументы есть в её схеме, обязательные заданы, значения
  без шаблонов проходят JSON-схему аргумента; явно абсолютные пути (`C:\…`, `/etc/passwd`,
  `/data/x.json`, `~/…`) отклоняются уже здесь — где бы в аргументе они ни были, в
  списке вложений тоже (текст вроде «/start» путём не считается), остальное не
  пропустит песочница executor при запуске;
- шаблоны компилируются, фильтры известны;
- шаблон ссылается только на переменные, шаги выше (в своей ветке `foreach`), `today`,
  `now` и глобальные имена Jinja (`range`, `dict`…) — ровно то, что есть у запуска;
- ссылка `шаг.output.поле.…` существует в output-схеме команды, пока схема описывает
  поля (свободные результаты вроде `llm.extract.data` дальше не проверяются).

По чату (только при сборке):

- если в чате что-то делалось, задача повторяет хотя бы одно действие, которое выполнилось
  успешно (команда, опробованная через `tools.try`, тоже считается). Чат без действий —
  «каждое утро пришли мне «Доброе утро»» — тоже собирается: проверять там нечего. Вызов, на
  который пользователь не сказал «да», компилятор видит как «НЕ выполнено: пользователь не
  подтвердил» и в задачу не берёт, если тот потом сам об этом не попросил;
- значения, которые пользователь задал сам (номер, клиент, текст), — в аргументах как
  есть: у задачи нет ввода при запуске, и пустая переменная — ошибка;
- текст из чата не переписан с ошибками: строка от 15 символов, которая совпадает с
  фрагментом разговора на 90% и больше, но не дословно, отклоняется с оригиналом.

Проверки по каталогу без LLM есть и отдельным маршрутом компилятора —
`POST /validate` с задачей в теле; через main он не выставлен.

## Правки

Правка всегда создаёт черновик новой версии с diff и одобрением; активная версия
работает, пока новую не одобрят.

- **Словами:** `task_patch` в чате → `POST main/compiler/patch {task_id, instruction}`.
  Модель возвращает JSON Patch (RFC 6902) и одну фразу итога; патч применяется и
  проходит проверки по каталогу.
- **Вручную, без LLM:** `POST /tasks/{id}/versions` с `ops` (JSON Patch) или `spec`
  (задача целиком), см. [API.md](API.md#задачи).
- **С командами, как они есть сейчас:** `POST /tasks/{id}/tools/refresh` — те же шаги,
  новые определения команд, см. [ниже](#команды-задачи).

Правка строится от **самого свежего черновика** после активной версии, а если его нет —
от активной: вторая правка подряд сохраняет первую. Прежние черновики становятся
`superseded`, их одобрения — `cancelled`. Правка, которая ничего не меняет, отклоняется.
Diff черновика показывает разницу с **активной версией** — то, что изменит его одобрение,
вместе с правками черновиков до него.

**diff** считается по шагам: добавлен, убран, изменён (текст карточки, аргументы,
а также команда, условие `when`, перебор, `on_error`, `on_empty`, `retries`), порядок
шагов, переменные, описание, расписание и название — строками «было → стало»; и по
командам: «изменилась команда `x.y`: аргументы, код».

Правка готовится на версии, которая была последней в момент запроса. Если, пока модель
думала, задачу успели изменить ещё раз, правка не сохраняется (`409`): чужая правка не
пропадает незаметно.

## Одобрение

Одобрение одно — версии задачи, и даёт его только пользователь:
`POST /tasks/{id}/versions/{v}/approve`. У агента такого инструмента нет. Отдельной
записи у одобрения нет: решения ждёт сам черновик версии (`GET /approvals` — список
черновиков), новый черновик заменяет прежний.

Черновик одобряется только с теми командами, что он показывает: если команда изменилась
после черновика, одобрение отклоняется (`409`, `tools_changed`), и задачу пересобирают
с командами, как они есть.

При одобрении версия становится активной (`current_version_id`), прежняя активная —
`superseded`; название и описание задачи берутся из версии; настройки приводятся к
командам версии (см. ниже); задача из `draft` или `archived` становится `active`.
Затем main просит scheduler перечитать задачу.

Перед одобрением пользователь может попросить пробный запуск: исполняется черновик, а
команды, которые что-то меняют, только пишут, что сделали бы (см.
[RUNS.md](RUNS.md#пробный-запуск)). Результат, включая ошибки, приходит в чат как
есть, ничего автоматически не чинится. Одобрить можно и после неудачного пробного
запуска — это решение пользователя.

## Команды задачи

Версия задачи хранит определение каждой команды, которую вызывают её шаги
(`task_versions.tools`, `common/tools/definition.py`), — у встроенной и своей
одинаково. Определение — то, что команда делает: описание, схемы аргументов и
результата, настройки, подтверждение, аккаунты, тайм-аут и у команды плагина хеш его кода.
Как команда показана (карточка, название, руководство группы), в него не входит. Из
определения считается хеш; каталог (`GET /tools`) отдаёт его у каждой команды (`hash`).

Задача работает только с командами, с которыми её одобрили:

- **runner перед запуском** сверяет хеши всех команд версии с каталогом. Не совпало
  (команду изменили, удалили, или версия из времён до хешей) — запуск закрывается
  `failed` ещё до первого шага (`result.tools_changed`), и main узнаёт об этом
  (`POST /internal/tools-changed`);
- **executor на каждом вызове** получает от runner хеш (`hash` в `_meta` вызова `tools/call`) и не
  запускает команду, если она уже другая (`tool_changed`). Запуск на этом останавливается,
  каким бы ни был `on_error` шага;
- **main** ставит задачу на паузу (вместе с расписанием) и пишет в её чат, какие команды
  изменились, а каких больше нет. Пробный запуск только сообщает об этом в своём результате.

Панель задачи показывает, что изменилось (`tool_changes` в `GET /tasks/{id}`), и
кнопку «Посмотреть задачу с новыми командами»: `POST /tasks/{id}/tools/refresh` создаёт
черновик с теми же шагами и командами, как они есть, с diff по командам. Дальше — как с
любым черновиком: пробный запуск, одобрение, затем «Возобновить». Если шаги не подходят к
новым схемам, черновик не создаётся (`422` со списком), и задачу правят словами. Если
команды больше нет, обновлять нечем (`409`): её шаги убирают словами в чате задачи или
возвращают команду; если не запущен её плагин — ждут, пока он запустится.

Любая правка тоже берёт команды, как они есть сейчас, и её diff говорит, что в них
изменилось.

## Статусы

| Объект | Статус | Что значит |
| --- | --- | --- |
| Задача | `draft` | Одобренной версии ещё нет; по расписанию не запускается |
| Задача | `active` | Есть активная версия, расписание работает |
| Задача | `paused` | Расписание выключено, вручную запустить можно |
| Задача | `archived` | Скрыта из списка, история сохранена |
| Версия | `draft` | Черновик, ждёт решения |
| Версия | `approved` | Активная версия задачи |
| Версия | `superseded` | Заменена: прежняя активная после одобрения новой или черновик, на котором построен более новый |
| Версия | `rejected` | Отклонена. Задача, которую ни разу не одобряли, без других черновиков уходит в архив: от неё ничего не осталось |

Переходы задачи: `pause` — из `active`; `resume` — из `paused`; `archive` — из `draft`,
`active`, `paused`. В архиве задачу никто не ждёт: ожидающие одобрения её черновиков
закрываются как `cancelled`.

## Настройки

Команда может объявить настройки — то, что выбирает только пользователь (см.
[TOOLS.md](TOOLS.md#настройки-команды)). Например, `mail.send`: `send_directly`,
отправлять ли письма сразу (по умолчанию `false`: письмо ложится в черновики, отправляет
человек). У значения три уровня:

- **по умолчанию** — из объявления команды;
- **для всей задачи** — одно значение для всех шагов с этой командой;
- **для шага** — своё значение у одного шага (по его `id`).

Шаг работает со своим значением, иначе со значением задачи, иначе со значением по
умолчанию; runner передаёт executor'у итог для каждого шага. Задача хранит только то,
что пользователь поменял, по группе и команде:

```json
{"mail": {"mail.send": {"send_directly": {"all": true, "steps": {"to_client": false}}}}}
```

- Меняет значения **только пользователь**: `PATCH /tasks/{id}/settings` (см.
  [API.md](API.md#задачи)). Компилятор и модель значений не выбирают; агент только
  пересказывает значения задачи.
- При новой версии изменения сохраняются для команд, которые в задаче остались, и для
  шагов с тем же `id` и той же командой; остальное отбрасывается.
- В чате действуют значения по умолчанию.
- В панели задачи настройки задачи — построчный список, а настройки шага — внизу
  раскрытого шага, под командой и аргументами.

## Карточки

Для человека каждая версия хранит карточки шагов: фраза из шаблона `card` команды с
подставленными аргументами («Взять файлы «*.xlsx» из папки «Отчёты/Продажи»»), для
`foreach` — «Для каждого элемента из …» с вложенными карточками. Шаблоны в аргументах
показываются словами: `{{ week_start }}` — как `‹week_start›`, фильтры только для печати
(`format_date`, `format_number` и подобные) опускаются, `| length` читается как «число …»,
`{% for f in files %}…{% endfor %}` — как «для каждого из ‹files›: …», `{{ loop.index }}`
— как «№». Аргумент, которого нет в шаге, показывается своим значением по умолчанию
(«из папки «INBOX»»), а часть карточки, все аргументы которой пусты, опускается:
«Пометить письма 3 в «Test»», а не «…: прочитано — —, важное — —». Расписание описывается словами: «по понедельникам в
10:00», «по будням в 09:00», «каждый месяц 1-го числа в 09:00».
