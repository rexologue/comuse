# План переработки: каждая сущность знает только своё

Итог обсуждения после ревью (октябрь 2026). Один шаг — один коммит; SPEC.md правится в том же коммите, что и код.

## Решения

**Сервисы**

- **scheduler** знает только «когда»: cron или ручной запуск.
- **runner** исполняет шаги по порядку и ведёт журнал запуска. Человека он не ждёт никогда.
- **executor** только исполняет команду:
  - находит её и проверяет аргументы по схеме;
  - проверяет аргументы-пути по их типу (песочница: рабочая папка и `data:templates` / `data:outputs`);
  - достаёт секреты для аргументов, которые команда объявила секретами;
  - пробный запуск ведёт по объявлению команды `dry_run`;
  - вызывает с таймаутом и возвращает результат.

  Прав задачи, подтверждений и собственного хранилища у него нет.
- **agent-loop** ведёт чат. Перед внешним действием (`side_effect: external`) спрашивает пользователя сам.
- **compiler** собирает задачу из одного чата и проверяет её. Ничего не запускает: черновик уходит в чат.

**Задача и её одобрение**

- **Права задачи — это одобренные аргументы её шагов.** Отдельного блока `permissions` нет. Ограничения на значения, которые станут известны только при запуске, — обычные аргументы команды, проверяет их сама команда (`mail.send.allow_to: ["*@company.ru"]`).
- **Одобрение одно — задачи**, после компиляции и после каждой правки. В чате пользователь решает:
  - **deny** — правки словами, агент правит задачу;
  - **dry-run** — пробный запуск по запросу, результат в чат;
  - **approve** — задачу включает только пользователь, у агента такого инструмента нет.
- **Запуск никогда не ждёт человека.** Нет `user.ask` и `ask_user`. Где нужен человек, команда оставляет результат вне запуска: письмо в черновиках, файл в папке на проверку.
- **Поведение внешних действий** задают настройки группы команд (`mail.send_directly`). Их меняет только пользователь. Это уже сделано.

**Журнал и уведомления**

- **Один журнал на запуск.** Его ведёт runner: `task_id` + `run_id`, записи только добавляются (старт и метаданные, каждый шаг: аргументы, выход, ошибка с traceback, сообщения команды, конец). Смотреть: `GET /tasks/{id}/runs`, `GET /runs/{id}/log`. Срок хранения — `RUN_RETENTION_DAYS` (15), чистит runner вместе с `outputs/<run_id>`.
- **`user.notify`** пишет в журнал запуска и сообщением в чат, из которого собрана задача.

**Группы команд** приносят своё сами: настройки, вид аккаунта (пресеты, проверка входа), инструкции для агента и компилятора.

## Шаги

1. **Права — аргументы шагов.**
   - Убрать `permissions` из Task вместе с выводом прав в компиляторе, подписями в карточках, `check_recipients` и проверкой аккаунта в `ToolContext`, проверкой папок в `paths.py` и передачей прав runner → executor.
   - В `mail.send` и `mail.create_draft` добавить `allow_to` с проверкой внутри команды.
2. **Executor: секреты и пути по объявлениям команд.**
   - `secrets=("account",)`: executor сам достаёт аккаунт и пароль и кладёт в контекст.
   - Аргументы типа «путь» executor проверяет до вызова.
3. **Подтверждение в чате — в agent-loop.** Из executor уходит чат-политика (`needs_approval`, `confirmed`).
4. **Запуски без пауз.**
   - Убрать `user.ask`, `NeedsInput`, `ask_user` в `on_error` / `on_empty`.
   - Убрать паузу и продолжение в runner и одобрения `ask_user`.
5. **Единый журнал запуска.**
   - `runs` + журнал в runner, `GET /runs/{id}/log`, срок хранения.
   - Executor отдаёт всё в ответе (traceback, длительность, `ctx.log`), `tool_calls` и `step_runs` уходят.
   - `user.notify` — в журнал и в чат задачи.
6. **Компиляция без запуска.**
   - Compile только собирает и проверяет; агенту — `task_dry_run`.
   - У задачи ссылка на её чат, у версии — чат правки.
   - Ручная правка без LLM: `POST /tasks/{id}/versions` (JSON Patch или целая спецификация) → проверки, diff, черновик, одобрение.
7. **Аккаунты от почтовой группы.** Executor хранит аккаунт как имя, вид, настройки и пароль в keyring. Вид `imap_smtp` с пресетами и проверкой входа объявляет почтовая группа.
8. **Инструкции групп вместо общих промптов.**
   - Группа приносит текст для агента и компилятора через каталог.
   - Признак «показывать всегда» — флаг в `@tool`.
   - Чтение документов — общий модуль, а не `docs.readers` из группы `llm`.
9. **Живая проверка и документация.** Сквозные сценарии отчёта и автоответчика на GreenMail; SPEC.md без раздела «Известные проблемы».
