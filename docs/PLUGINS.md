# Плагины

Всё, что агент умеет сверх встроенных команд из `internal_tools/`, — плагины. Плагин —
группа команд (`telegram` → `telegram.send`, `telegram.read`) со своим кодом, своими
пакетами и своим процессом: MCP-сервером, который executor запускает сам и чьи
инструменты отдаёт как свои ([TOOLS.md](TOOLS.md#серверы-mcp)). Группу встроенных
команд (`mail`, `fs`…) плагин занять не может.

Плагины бывают двух видов, а всё остальное у них общее:

| Вид | Что в манифесте | Кто сервер | Чей |
| --- | --- | --- | --- |
| Функции | `tools`: команды и их файлы с `def run(args, ctx)` | наша обёртка `executor/plugins/shim.py` | ваши и чата |
| Свой сервер | `command`: как его запустить | сам плагин (готовый MCP-сервер) | откуда угодно |

Код — `executor/plugins/`, API и таблица — у executor.

## Папка плагина

У плагина есть одобренный код (`current`, он работает) и, может быть, черновик (`draft`).
Каждый — своя папка:

```
DATA_DIR/plugins/<группа>/{current,draft}/
  plugin.json         манифест
  …                   код и небольшие файлы данных (.py, .json, .txt, .csv, .md, .yaml, .toml)
  requirements.txt    пакеты, которые плагин объявил
  requirements.lock   точные версии всех пакетов с хешами
  .venv/              своё окружение
```

Имя (группа) — латиница в нижнем регистре, цифры и `_`. Хеш кода считается по всем
файлам, кроме `.venv`, и хранится в базе.

### plugin.json: функции

```json
{
  "title": "Разбор документов",
  "tools": [
    {
      "name": "parse_date",
      "title": "Разобрать дату",
      "description": "Переводит дату в свободной форме в ISO 8601",
      "card": "Разобрать дату «{text}»",
      "confirm": false,
      "timeout": 60,
      "entry": "parse_date/main.py",
      "input_schema": {"type": "object", "properties": {"text": {"type": "string"}}, "required": ["text"]},
      "output_schema": {"type": "object", "properties": {"iso": {"type": "string"}}, "required": ["iso"]}
    }
  ]
}
```

| Поле команды | Что это |
| --- | --- |
| `name` | Имя в группе: команда будет `<группа>.<name>` |
| `title`, `description` | Название и описание: по описанию модель выбирает команду |
| `card` | Что видит пользователь перед вызовом, с `{аргумент}`; пусто — `title` |
| `confirm` | `true` — спросить, `"always"` — каждый раз, `false` — не спрашивать (только смотрит или считает) |
| `timeout` | Секунды; пусто — `timeout` плагина, иначе `tool_timeout_sec` |
| `entry` | Файл с `def run(args, ctx)`; его соседние модули импортируются как обычно |
| `input_schema`, `output_schema` | JSON Schema объекта. Аргумент с `"x-path": "path"` (у списка — в `items`) — путь в рабочей папке: executor проверяет его до вызова и передаёт полным путём |

```python
from agent_tool import ToolError   # ошибка для пользователя без traceback


def run(args, ctx):
    ...
    out = ctx.output_path("итог.txt")    # файл в результатах запуска, станет артефактом
    ctx.log("строк: 3")                  # строка в журнал запуска или трассу чата
    if ctx.dry_run:                      # пробный запуск: ничего не менять
        ...
    return {"iso": "...", "file": str(out)}
```

`ctx`: `mode` (`chat` / `run`), `dry_run`, `output_dir`, `run_id`, `step_key`,
`session_id`, `log(text)`, `notify(text)` (сообщение пользователю в чат задачи),
`output_path(filename)`. Ответ — JSON-объект по `output_schema`; полные пути в нём
executor переводит обратно в `Отчёты/x.xlsx` / `data:outputs/…`. Что функция печатает,
не сохраняется: stdout занят протоколом.

Обёртка — только стандартная библиотека Python: в `.venv` плагина ровно его пакеты,
ни нашего, ни SDK MCP. Она отвечает на `initialize`, `tools/list`, `tools/call`, `ping`;
вызовы идут каждый в своём потоке.

### plugin.json: свой сервер

```json
{
  "title": "Почта (mcp-email-server)",
  "command": ["mcp-email-server", "stdio"],
  "env": {"MCP_EMAIL_SERVER_LOG_LEVEL": "WARNING"},
  "confirm": true,
  "confirm_by_tool": {"list_emails_metadata": false},
  "timeout": 120
}
```

| Поле | Что это |
| --- | --- |
| `command` | Первое слово — `python` (из `.venv` плагина) или программа из `.venv` плагина (скрипт пакета); ничего с остальной машины. Остальное — аргументы |
| `env` | Переменные процесса сверх безопасных (`PATH`, `HOME`, локаль) |
| `confirm`, `confirm_by_tool` | Спрашивать ли перед вызовом — для всех инструментов и для каждого (по имени на сервере). Подсказки самого сервера (`readOnlyHint`) — только его слова |
| `dry_run` | Сервер сам делает пробный запуск (по `_meta.context.dry_run`). По умолчанию у функций — да, у своего сервера — нет |
| `timeout` | Секунды на вызов |
| `path_args` | Какие аргументы сервера — пути в рабочей папке, по инструментам: `{"send_email": {"attachments": "refs"}, "download_attachment": {"save_path": "path"}}` (`path` — один путь, `refs` — список). Сервер о нашей рабочей папке не знает и пометить их сам не может; executor проверяет их песочницей и передаёт полными путями, как у своих команд, а полные пути в ответе возвращает ссылками. Не помеченный путь executor не видит: сервер прочитает или запишет любой файл, доступный пользователю |
| `hidden_tools` | Инструменты сервера, которых модель не видит вовсе (по именам на сервере): сырая команда протокола, то, чего плагину здесь делать не нужно |
| `account` | Плагин работает от имени аккаунта — см. [ниже](#аккаунты) |

Инструменты такого плагина известны, только когда сервер запущен, поэтому перед
одобрением черновик запускают один раз («Проверить запуск»).

## Аккаунты

Плагин, который работает от имени аккаунта (почтовый ящик, бот), объявляет его в
манифесте. Пример — готовый сервер почты на аккаунтах нашего вида `imap_smtp`:

```json
"account": {
  "kind": "imap_smtp",
  "argument": "account_name",
  "env": {
    "MCP_EMAIL_SERVER_ACCOUNT_NAME": "${account.name}",
    "MCP_EMAIL_SERVER_EMAIL_ADDRESS": "${account.email}",
    "MCP_EMAIL_SERVER_USER_NAME": "${account.username}",
    "MCP_EMAIL_SERVER_PASSWORD": "${account.secret}",
    "MCP_EMAIL_SERVER_IMAP_HOST": "${account.imap_host}",
    "MCP_EMAIL_SERVER_IMAP_PORT": "${account.imap_port}",
    "MCP_EMAIL_SERVER_IMAP_SSL": "${account.imap_security|ssl=ssl}",
    "MCP_EMAIL_SERVER_IMAP_START_SSL": "${account.imap_security|ssl=starttls}"
  }
}
```

| Поле | Что это |
| --- | --- |
| `kind` | Вид аккаунта: встроенный (`imap_smtp`) или, с `fields`, свой |
| `fields`, `title`, `secret_title` | Свой вид: поля формы аккаунта (`name`, `title`, `type`: text/number/choice, `required`, `choices`, `hint`, `default`), его название, как называется секрет. Вид появляется на странице «Аккаунты», пока плагин одобрен; занять чужой вид нельзя |
| `env` | Переменные процесса из аккаунта: `${account.name}`, `${account.secret}`, `${account.<поле>}`, `${account.<поле>\|по умолчанию}`, `${account.<поле>\|по умолчанию=значение}` (`true`, если поле — или его значение по умолчанию — равно значению, иначе `false`). Переменная, которая вышла пустой, не задаётся вовсе: для сервера пустая — заданная |
| `argument` | Аргумент сервера, который называет аккаунт: модель его не видит, executor заполняет именем аккаунта |

- **Аргумент `account`.** У каждого инструмента плагина модель видит наш обычный
  обязательный аргумент `account` — имя аккаунта из настроек (как у встроенной почты), а
  аргумента сервера (`argument`) не видит. Executor загружает аккаунт до вызова:
  неизвестный аккаунт или аккаунт без пароля — отказ, аккаунт другого вида — тоже.
- **Процесс на аккаунт.** У каждого аккаунта — свой процесс сервера, и только в его
  окружении настройки и секрет этого аккаунта: ни в аргументах процесса, ни в файлах, ни
  в журналах их нет. Процесс запускается при первом вызове с этим аккаунтом; изменились
  настройки или пароль аккаунта — следующий вызов идёт в новый процесс.
- **Каталог.** Инструменты плагина в каталоге даёт процесс первого аккаунта этого вида (по
  имени), а пока аккаунтов нет — процесс без аккаунта. Когда аккаунт этого вида создают,
  меняют или удаляют, плагины этого вида запускаются заново.
- Подстановки аккаунта бывают только в `account.env`: аргументы процесса видны в
  списке процессов, а общий `env` плагина — в каждом его процессе.

## Пакеты

Пакеты ставит uv (зависимость проекта, поэтому он есть везде, где стоит агент):

1. при сохранении черновика `requirements.txt` разрешается в `requirements.lock`:
   точные версии всех пакетов, включая транзитивные, с хешами. Этот список видит тот,
   кто одобряет черновик;
2. при одобрении — заново, с пустой папки (что оставил в `.venv` пробный вызов черновика,
   в одобренный код не попадает), а при запуске, если `.venv` пропал, —
   `uv venv` на интерпретаторе агента и `uv pip sync --require-hashes --only-binary :all:`.

В `requirements` — по одному пакету из индекса в строке: строки с переводом строки,
опциями (`-r`, `-e`, `-c`…), путями и URL отклоняются. Ставятся только готовые
wheel-пакеты: при установке wheel код пакета не выполняется. Кеш uv —
`DATA_DIR/cache/uv`. Индекс — PyPI или зеркало из `UV_INDEX_URL`; без сети работают только
плагины без пакетов.

## Жизнь черновика

```
черновик ──проверить запуск (свой сервер)──▶ инструменты видны ──одобрил человек──▶ одобренный код
   │
   └──выбросили──▶ удалён
```

- **Черновик** у плагина один. Его можно сохранять сколько угодно раз: папка
  переписывается (`.venv` переиспользуется). При каждом сохранении проверяются имя,
  манифест, файлы (только внутри папки, разрешённые расширения, размер), что `.py`
  компилируется, что у функций есть их файлы и что пакеты разрешаются (в отдельной папке
  до записи). Все несовпадения — одной ошибкой, и тогда ничего не записано. Чат не
  заменяет черновик, который написал человек или другой чат.
- **Одобряет только человек**, увидев код, пакеты и инструменты. Одобрение называет хеш
  черновика, который человек видел: если черновик переписали, пока карточка была
  открыта, одобрение отклоняется. Если файлы изменились после сохранения — тоже.
  После одобрения папка черновика становится `current` (прежний код удаляется), заново
  ставятся пакеты, и executor запускает сервер плагина.
- **Одобренный код не меняется.** Перед запуском сервера executor сверяет файлы с хешем;
  не совпало — сервер не запускается, и инструментов плагина в каталоге нет.
- **Задачи с командами плагина ждут решения.** Новый код — другое определение команд
  (`code_hash`), поэтому задачи, которые их вызывают, не запускаются, пока пользователь
  не посмотрит изменения и не одобрит каждую с ними ([TASKS.md](TASKS.md#команды-задачи)).

## Сервер плагина

Executor запускает одобренные плагины при старте (до того, как начнёт принимать
запросы) и после одобрения; держит с каждым сессию по stdio; падение — перезапуск при
следующем вызове; вызов, на который истёк таймаут, — остановка процесса (следующий вызов
запускает его заново). Процесс получает чистое окружение: никаких токенов и ключей
агента. Его домашняя папка (`HOME`, `XDG_*`, на Windows `USERPROFILE`, `APPDATA`) —
`DATA_DIR/plugins/<имя>/home`: что сервер хранит для себя (кеш, свои настройки),
остаётся с плагином, а не в домашней папке пользователя и не в одобренном коде; при
удалении плагина она удаляется с ним. Наше, чего нет в MCP, едет в `_meta`: контекст вызова — к серверу, его логи,
сообщения и созданные файлы — обратно; сторонний сервер их не знает и просто не
пользуется.

**Пробный запуск.** Плагин, который сам делает пробный запуск (`dry_run`), вызывается
как обычно. У остальных в пробном запуске вызываются только инструменты, которые ничего
не меняют (`confirm: false`); вместо остальных в журнале — «не вызван, вызвал бы с …»,
а результат шага пустой.

Это не песочница: код может прочитать то, что может пользователь, и выйти в сеть.
Безопасным плагин делает человек, который прочитал и одобрил его.

## В интерфейсе

«Настройки» → «Плагины»: плагины с одобренным кодом и черновиком, инструментами,
пакетами, работает ли сервер (и почему нет); проверить запуск, одобрить, выбросить
черновик; «Править черновик» и «Черновик на основе этого кода» (манифест, файлы, пакеты);
перезапустить, удалить плагин; ниже — встроенные команды.

## Из чата

Агент пишет свои команды сам, командами группы `tools` (только в чате):

1. `tools.list` — какие плагины уже есть; доработать — сначала `tools.show` (код и пакеты);
2. `tools.draft` — записать одну команду `группа.действие` в черновик плагина этой
   группы: её схемы, файлы (лягут в `<действие>/`), пакеты; остальные команды плагина
   остаются как были. Ничего не запускается; ошибки проверки приходят все сразу;
3. `tools.try` — вызвать команду черновика на настоящем файле пользователя. Спрашивает
   «да» каждый раз: код не одобрен;
4. агент говорит, что черновик готов. В этом чате появляется карточка: команды, пакеты,
   код, «Одобрить» и «Выбросить». Одобрить может только человек.

## API

Через main, с токеном внешнего API.

| Маршрут | Что делает |
| --- | --- |
| `GET /plugins` | Плагины: `current` и `draft` каждого (кто и когда записал, хеш; нет — `null`), `running`, `error`, `tools` — инструменты работающего сервера |
| `GET /plugins/{name}/current`, `…/draft` | Одобренный код или черновик: манифест, пакеты, `tools` (что человек видит перед одобрением; `null` — сервер ещё не запускали), файлы, `requirements` |
| `PUT /plugins/{name}/draft` | Сохранить черновик: `{"manifest", "files", "requirements"}` |
| `POST /plugins/{name}/draft/check` | Запустить сервер черновика один раз и запомнить его инструменты (по просьбе человека) |
| `POST /plugins/{name}/draft/approve {hash}` | Одобрить черновик, который человек видел |
| `DELETE /plugins/{name}/draft` | Выбросить черновик |
| `POST /plugins/{name}/restart` | Запустить сервер заново |
| `DELETE /plugins/{name}` | Удалить плагин: сервер, одобренный код и черновик |

Ошибки проверки и установки — `400` с текстом, что не так.

## Откуда пришли

Раньше свои команды были отдельной сущностью (`external_tools`). Миграция `0009`
превратила каждую их группу в плагин функций — черновик: команды легли в
`<действие>/`, их манифесты — в `tools`, пакеты — в общий `requirements.txt`. Executor
при старте подбирает такому черновику пакеты; одобряет его человек.
