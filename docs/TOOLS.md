# Команды

Этот документ описывает, как устроена команда, как executor её вызывает и что умеет
каждая группа команд.

Команды лежат в `internal_tools/<группа>/`: одна команда — один Python-файл с
декоратором `@tool` (или пара команд с общим входом, как `fs.copy` и `fs.move`). Схемы,
описание для модели и шаблон карточки — в том же файле, отдельной регистрации нет:
executor при старте сам обходит `internal_tools/`. Внутренний
`POST /executor/tools/reload` подхватывает новые файлы команд, но не правки
существующих: для них executor нужно перезапустить. Посмотреть каталог: `GET /tools`.

Группа команд приносит своё сама: настройки для задач, вид аккаунта, инструкции для
агента и компилятора, поведение в пробном запуске. За пределами группы никто не
знает, что значат её команды.

## Как написать команду

```python
# internal_tools/mail/send.py (сокращённо)
class Input(ToolInput):
    account: str = Field(description="Имя почтового аккаунта отправителя")
    to: list[EmailAddress] = Field(min_length=1)
    cc: list[EmailAddress] = Field(default_factory=list)
    subject: str
    body: str
    attachments: list[WorkspacePath] = Field(default_factory=list, description="Пути файлов для вложения")


class Output(ToolOutput):
    message_id: str
    mode: str                      # "sent" или "draft"
    folder: str | None = None


@tool(
    name="mail.send",
    title="Отправить письмо",
    card="Отправить письмо {to} с темой «{subject}»",
    description="Send an email ... a dry run always saves a draft.",
    confirm="always",              # в чате спрашивать перед каждым письмом
    secrets=("account",),          # executor загрузит аккаунт по имени
    timeout=120,
)
async def send(inp: Input, ctx: ToolContext) -> Output:
    account = mailbox(ctx)         # настройки и пароль, уже загруженные executor
    message = imap_smtp.build_message(...)

    if ctx.dry_run or (ctx.mode == "run" and not ctx.domain_settings(MailSettings).send_directly):
        folder = await asyncio.to_thread(imap_smtp.append_draft, account.config, account.secret, message)
        return Output(message_id=message["Message-ID"], mode="draft", folder=folder)

    await asyncio.to_thread(imap_smtp.send, account.config, account.secret, message)
    return Output(message_id=message["Message-ID"], mode="sent")
```

Сигнатура — `async def (inp, ctx) -> Output`: аннотация первого параметра — модель
входа (наследник `ToolInput`, лишние аргументы — ошибка), возвращаемая — модель
результата. Из них строятся JSON-схемы для модели, для проверки вызова и для проверки
ссылок `шаг.output.поле` в задачах. Блокирующую работу (файлы, сеть, документы) команда
уносит в поток `asyncio.to_thread`, чтобы не останавливать executor.

## Манифест

| Поле `@tool` | Зачем |
| --- | --- |
| `name` | `группа.действие`; по нему на команду ссылаются шаги задачи. Модели оно передаётся как `группа__действие` |
| `title`, `card` | Название и шаблон фразы карточки шага: `{аргумент}` подставляется |
| `description` | Описание для модели |
| `confirm` | Спросить ли пользователя в чате перед вызовом: `True` (по умолчанию) — да, и пользователь может разрешить команду на весь чат; `"always"` — каждый раз; `False` — команда только смотрит или считает, а файлы создаёт только в результатах запуска |
| `secrets` | Аргументы, которые называют сохранённый аккаунт; executor загружает его и отдаёт как `ctx.credential(<аргумент>)` |
| `timeout` | Секунды до отмены; по умолчанию настройка [`tool_timeout_sec`](SETTINGS.md) (300) |
| `core` | Показывать агенту всегда, вне зависимости от отбора по смыслу (сейчас `fs.list`, `docs.read`) |

`GET /tools` отдаёт по каждой команде манифест: эти поля, `function_name`,
`input_schema`, `output_schema`, а также `settings_schema` и `guide` её группы.

**Типы аргументов**, которые понимает executor (`common/tools/fields.py`, `refs.py`):

| Тип | Что это |
| --- | --- |
| `WorkspacePath` | Путь к файлу или папке; executor проверяет его до вызова |
| `FileRefs` | Файлы: путь, список путей или результат `fs.list` целиком; executor проверяет каждый путь до вызова |
| `TextOrFileRefs` | Путь, список путей или обычный текст (входы `llm.*`); заранее не проверяется, файлы из него открываются через `ctx.read_path` |
| `EmailAddress` | Адрес почты: одна `@`, без пробелов и разделителей; доставляемость решает сервер |

## Контекст команды

`ctx: ToolContext` — всё, что команде нужно, кроме входа:

| Что | Зачем |
| --- | --- |
| `ctx.mode` | `chat` — вызов из чата, `run` — шаг запуска задачи |
| `ctx.dry_run` | Пробный запуск (см. ниже) |
| `ctx.credential("account")` | Аккаунт из `secrets`: `name`, `kind`, `config`, `secret` |
| `ctx.domain_settings(Модель)` | Настройки группы у задачи; в чате — значения по умолчанию |
| `ctx.read_path(ref)`, `ctx.write_path(ref)`, `ctx.to_ref(path)` | Путь задачи → файл через песочницу и обратно |
| `ctx.output_path(имя)`, `ctx.output_dir()` | Новый файл в `data:outputs/<запуск или чат>/`; путь попадает в список созданных файлов |
| `ctx.log(текст)` | Строка в журнал запуска (или трейс чата) рядом с результатом вызова |
| `ctx.notify(текст)` | Сообщение пользователю: в журнал запуска и в чат задачи |
| `ctx.llm` | Клиент LLM для команд `llm.*` |

Ожидаемая неудача — `raise ToolError("понятный текст")`: текст увидят пользователь и
модель. Выход за пределы песочницы — `PermissionDenied`.

## Вызов команды

И чат, и runner вызывают команду одинаково: `POST main/executor/execute`.

```json
{"tool": "fs.move", "args": {"src": "Входящие/a.pdf", "dst": "Счета/"},
 "context": {"mode": "run", "run_id": "run_…", "step_key": "sort[0].move", "task_settings": {"mail": {"send_directly": false}}, "dry_run": false}}
```

Конвейер:

1. найти команду;
2. проверить аргументы по схеме входа (ошибка — «Неверные аргументы»);
3. проверить аргументы-пути (`WorkspacePath`, `FileRefs`) песочницей (ошибка — «Нет доступа»);
4. загрузить аккаунты для аргументов из `secrets` (неизвестный аккаунт — отказ до вызова);
5. вызвать с таймаутом;
6. проверить результат по схеме результата.

Ответ:

```json
{"status": "ok", "output": {"path": "Счета/a.pdf"}, "error": null, "artifacts": [],
 "duration_ms": 12, "traceback": null, "logs": [], "notifications": []}
```

`status` — `ok` или `error`. Своего журнала у executor нет: длительность, traceback
(при сбое команды), строки `ctx.log` и сообщения `ctx.notify` уходят в ответе — даже
при ошибке — в журнал вызывающего. Executor ничего не спрашивает и прав задачи не
знает: кто вызывает, тот уже решил, что вызов нужен.

## Пути

Задачи хранят только переносимые ссылки, поэтому одна задача работает и на Windows, и
в контейнере:

- `Отчёты/Продажи/q3.xlsx` — от рабочей папки (настройка [`workspace_dir`](SETTINGS.md));
- `data:templates/weekly.docx`, `data:outputs/…` — внутри `DATA_DIR`.

Песочница (`executor/paths.py`) нормализует путь и отказывает, если он выходит за
рабочую папку (`..`, симлинк наружу), ведёт в `DATA_DIR` дальше `templates` и
`outputs` (база и секреты недоступны) или абсолютный и не внутри рабочей папки.
Обратные слэши Windows понимаются. С какими файлами работает задача, решают её
одобренные шаги; песочница лишь держит их внутри папки пользователя.

**Имена новых файлов и папок.** `ctx.write_path` не даёт создать то, что Windows не
примет: имя с `< > : " | ? *` или управляющими символами, кончающееся пробелом или
точкой, зарезервированное (`CON`, `NUL`, `COM1`…). Рабочая папка часто — папка Windows
или сетевая, а задача, собранная на Linux, должна работать и там. Ошибка подсказывает
годное имя: «Имя «2026-10-22T12:00:00.txt» не подойдёт для Windows: в нём «:».
Например: «2026-10-22T12-00-00.txt»». Уже существующие файлы и папки не проверяются: их
можно перезаписать или переложить. Файлы, которые команды называют сами в
`data:outputs` (`xlsx.write_table`, `charts.*`), просто получают `_` вместо таких
символов.

## Пробный запуск

Executor выполняет каждый вызов и только передаёт флаг `ctx.dry_run`. Что он значит,
решает команда:

- команда с `confirm=False` выполняется как обычно;
- **команда, о которой чат спрашивает, обязана проверить флаг сама:** проверить всё,
  как при настоящем вызове, ничего не изменить и написать в `ctx.log`, что сделала бы.
  `fs.move` — «Пробный запуск: переложил бы «a.pdf» в «Счета/a.pdf»», `mail.mark` —
  «письмо не тронуто; было бы: прочитано — да», `docs.make_template` — сохраняет шаблон в
  результаты запуска, а не в `data:templates`. `mail.send` и `mail.create_draft` кладут
  письмо в черновики: это и есть безопасный результат.

Что правило соблюдено, проверяет тест по всему каталогу
(`tests/test_executor_policy.py`): команда с `confirm` не `False`, в коде которой нет
`dry_run`, его не пройдёт.

## Настройки группы

Группа может объявить одну плоскую модель настроек для задач:

```python
@domain_settings
class MailSettings(DomainSettings):
    domain: ClassVar[str] = "mail"

    send_directly: bool = Field(
        default=False,
        title="Отправлять письма сразу",
        description="Выключено — письма из задачи сохраняются в черновики, отправляет их человек. ...",
    )
```

Поля — простые значения (булево, число, строка, выбор) с умолчанием, подписью и
описанием. Схема попадает в манифесты команд группы (`settings_schema`); модель её не
видит. Как настройки живут у задачи и кто их меняет — в
[TASKS.md](TASKS.md#настройки-групп-команд). Команда читает их через
`ctx.domain_settings(MailSettings)`.

## Виды аккаунтов

Executor хранит аккаунт как имя, вид, настройки и пароль (пароль — в хранилище
секретов, см. [SECURITY.md](SECURITY.md#секреты)). Что нужно виду, объявляет группа,
которой он принадлежит:

```python
account_kind(AccountKind(
    name="imap_smtp",
    title="Почта IMAP/SMTP",
    fields=(                  # настройки в config — как их спросить в форме
        AccountField("email", "Адрес почты", required=True),
        AccountField("imap_security", "Защита IMAP", type="choice", choices=("ssl", "starttls", "none")),
        ...
    ),
    secret_title="Пароль приложения",
    presets=PRESETS,          # готовые настройки известных провайдеров
    prepare=_prepare,         # дополнить и проверить настройки; ValueError — понятный текст
    check=imap_smtp.check,    # попробовать войти; POST /accounts/{name}/check
))
```

`GET /accounts/kinds` показывает виды: поля (`name`, `title`, `type` — `text`, `number`
или `choice`, `required`, `choices`, `hint`, `default` — что значит пустое значение),
как называется секрет, пресеты. По ним клиент строит форму, ничего не зная о почте.
`POST /accounts` создаёт аккаунт или меняет существующий с тем же именем; без `secret`
остаётся сохранённый пароль (см. [API.md](API.md#команды-и-аккаунты)). Имя не
меняется: по нему аккаунт называют задачи.

## Инструкции группы

Общий промпт агента и правила компилятора содержат только своё: работа через команды,
даты, пути, формат задачи. Как пользоваться почтой, файлами, отчётами, пишет сама
группа в `internal_tools/<группа>/guide.py`:

```python
domain_guide(
    "xlsx",
    agent="Все числа из таблиц (суммы, количества, топы) считай xlsx.aggregate — сам числа не складывай.",
    compiler="Числа считай xlsx.aggregate: число строк — .output.rows, суммы — .output.totals, группы — .output.groups.",
)
```

Инструкции идут в манифестах (`guide`). Агент получает инструкции групп, чьи команды
показаны ему на этом ходе, компилятор — всех групп каталога.

Полные схемы аргументов и результатов — `GET /tools`.

### Файлы (`fs`)

`fs.list` возвращает `files: [{path, name, size, modified}]`; `folder` пусто — корень
рабочей папки, `recursive` — и во вложенных папках, `modified_from` / `modified_to` —
даты `YYYY-MM-DD` включительно. Конкретные файлы из разговора компилятор обобщает
таким шагом: шаблон имени и даты периода. `fs.copy` и `fs.move` создают папку
назначения и не перезаписывают существующий файл без `overwrite`.

### Документы (`docs`)

Отчёт «такой же, как пример» делается в два шага. `docs.make_template` превращает
готовый отчёт в шаблон docxtpl: модель (`LLM_MODEL_INSTRUCT`) только указывает, что в
нём меняется от раза к разу, а документ правит код, поэтому оформление сохраняется.
Результат — путь шаблона, поля, таблицы и `example_context` — значения из примера в
готовом для заполнения виде. `docs.fill_template` заполняет шаблон: поля `{{ имя }}`,
циклы по строкам таблиц, картинки PNG. Если в `context` не хватает поля шаблона или у
строки таблицы нет нужной колонки, команда падает с объяснением, а не оставляет пустое
место.

### Таблицы (`xlsx`, `data`)

Числа в отчётах считает код, а не модель: `xlsx.aggregate` возвращает `rows` (число
строк), `totals` (суммы колонок), `groups: [{key, count, sums}]` (по `group_by`,
отсортированы по первой сумме, `top_n` — оставить первые N). Значения вроде `1 234,50`
понимаются как числа. `data.map_rows` готовит строки под колонки шаблона:
`fields: {"client": "row.key", "amount": "row.sums['Сумма'] | format_number"}` —
выражения без фигурных скобок, `limit` — сколько строк оставить.

### LLM (`llm`)

Команды для текста, которого нет в таблицах: извлечь поля (`llm.extract`, результат
проверяется по переданной JSON-схеме), выбрать категорию (`llm.classify` → `label`,
`reason`), написать текст (`llm.write`). Вход — текст, путь, список путей или результат
`fs.list`: файлы читаются в текст (до 60 000 символов у `llm.extract`, 20 000 у
`llm.classify`, 30 000 у `llm.write`). Используют `LLM_MODEL_INSTRUCT`.

### Почта (`mail`)

Одна группа поверх stdlib imaplib/smtplib, без привязки к провайдеру. Вид аккаунта
`imap_smtp`:

- обязательны `config.email`, `imap_host`, `smtp_host`; `username` по умолчанию — адрес (не сохраняется, берётся при входе);
- пресеты `gmail`, `yandex`, `mailru`, `outlook` заполняют серверы и порты; нужен пароль
  приложения, а не основной пароль ящика. Корпоративный сервер задаётся в `config`;
- соединение — `security` (или отдельно `imap_security` / `smtp_security`): `ssl`,
  `starttls` или `none`; SMTP входит, только если сервер предлагает AUTH;
- команды `mail.*` принимают только аккаунт этого вида.

Поведение команд:

- **`mail.search`** — от новых к старым, без писем с пометкой «удалено». Отправитель и
  тема сравниваются в самой команде по раскодированным заголовкам, а не поиском сервера
  (серверы ищут по-разному); заголовки запрашиваются пачками по 50. `sender` — подстрока для удобства
  поиска. **`sender_in`** — точный отбор: адреса или маски `*@домен`, сравнивается адрес
  отправителя целиком (`*@test.local` не пропустит `x@evil-test.local.com`). Компилятор
  заполняет его, когда задача что-то делает с найденными письмами. Результат —
  `messages: [{uid, sender, sender_email, to, subject, date}]`; для ответа берите
  `sender_email`.
- **`mail.read`** — текст письма (HTML упрощается до текста) и вложения, сохранённые в
  результаты запуска.
- **`mail.send`** — в чате отправляет после ответа пользователя; в задаче по умолчанию
  кладёт письмо в черновики, а отправляет сразу, только если пользователь включил
  настройку задачи `mail.send_directly`; в пробном запуске — всегда в черновики.
- **копия отправленного** — SMTP только доставляет письмо, копию у себя хранит почтовая
  программа. Поэтому после отправки `mail.send` кладёт письмо по IMAP в папку с флагом
  `\Sent` (или «Sent»; создаётся, если её нет; папка — `config.sent_folder`). Gmail и
  Outlook хранят копию сами: их пресеты ставят `save_sent: no`, иначе письмо было бы
  там дважды. Если копия не сохранилась, команда не падает (письмо уже ушло, повтор
  отправил бы его второй раз): причина — в `copy_error`.
- **черновик** — письмо в папке с флагом `\Drafts` (или «Drafts»; создаётся, если её
  нет); папку можно задать в `config.drafts_folder`.
- **`mail.mark`** — ставит или снимает «прочитано» и перекладывает письмо (папка
  создаётся). Перемещение — командой MOVE, а без неё — копия и пометка «удалено» у
  оригинала, который затем удаляется только сам (UID EXPUNGE), если сервер это умеет
  (UIDPLUS); иначе оригинал остаётся помеченным, и поиск его не показывает. Общий EXPUNGE
  не делается, чтобы не стереть письма, которые пользователь сам пометил удалёнными.
- Имена папок кодируются в modified UTF-7, кириллические папки работают.

`sender_in` отбирает по заголовку From, а его отправитель может подделать. Ответ на
такое письмо уйдёт на этот адрес, то есть в разрешённый домен, а не подделавшему, но
остальное задача с письмом сделает (переложит, обработает вложения). Проверка
подлинности по заголовку `Authentication-Results` своего сервера не реализована.

### Пользователь (`user`)

`user.notify {message}` — сообщение пользователю из задачи: в журнал запуска и в чат,
из которого задача собрана (см. [RUNS.md](RUNS.md#уведомления)). Ничего не ждёт.
