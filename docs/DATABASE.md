# База данных

Этот документ описывает хранилище: файл базы, правило владения таблицами и каждую
таблицу с полями и значениями.

Хранилище — один файл SQLite `DATA_DIR/app.db`. Отдельного сервиса нет: каждый сервис
работает с базой через общий пакет `common/storage` (SQLAlchemy 2). Режим
`journal_mode=WAL` и `busy_timeout=5000` позволяют нескольким процессам читать
одновременно с записью.

## Владение

**У каждой таблицы ровно один сервис-владелец: только он в неё пишет.** Остальные
читают напрямую или просят владельца через API. Так нет конфликтов записи и всегда
понятно, кто отвечает за данные.

| Таблица | Владелец | Кто ещё читает | Что хранит |
| --- | --- | --- | --- |
| [`events`](#events) | main | — | События для подписчиков SSE |
| [`settings`](#settings) | main | все сервисы | Рабочие настройки, изменённые через API, и назначение провайдеров LLM на роли |
| [`llm_providers`](#llm_providers) | main | agent-loop, compiler, executor | Провайдеры LLM (без ключей) |
| [`chat_sessions`](#chat_sessions) | agent-loop | — | Чаты |
| [`chat_messages`](#chat_messages) | agent-loop | — | Сообщения чатов (компилятор получает чат от agent-loop: `GET /agent/sessions/{id}/transcript`) |
| [`trace_events`](#trace_events) | agent-loop | — | Вызовы команд в чатах |
| [`tasks`](#tasks) | compiler | main, runner, scheduler, agent-loop | Задачи |
| [`task_versions`](#task_versions) | compiler | main, runner, scheduler, agent-loop | Версии задач |
| [`runs`](#runs) | runner | main | Запуски |
| [`run_log`](#run_log) | runner | main | Журналы запусков |
| [`accounts`](#accounts) | executor | — | Аккаунты (без паролей) |
| [`external_tools`](#external_tools) | executor | — | Свои команды: одобренный код и черновик, хеш файлов, манифест, пакеты |

Чего в базе нет:

- **паролей и ключей LLM** — только ссылка на запись или признак, что ключ есть; сами
  они в хранилищах секретов (см.
  [SECURITY.md](SECURITY.md#секреты));
- **каталога команд** — executor собирает его из `internal_tools/` и одобренного кода своих
  команд и отдаёт по `GET /tools`;
- **кода своих команд** — он в `DATA_DIR/external_tools/<группа>/<действие>/{current,draft}/`,
  в базе — его хеш;
- **расписания** — scheduler строит задания в памяти по активным версиям задач;
- **согласий «больше не спрашивай»** — они живут в памяти agent-loop до перезапуска;
- **файлов** — готовые документы лежат в `DATA_DIR/outputs/<запуск или чат>/`, шаблоны —
  в `DATA_DIR/templates/`.

Время хранится в UTC. SQLite не хранит часовой пояс, поэтому колонки времени —
`UTCDateTime` (`common/storage/db.py`): значение записывается в UTC и читается помеченным
как UTC, и в API время всегда приходит со смещением `+00:00`.

Идентификаторы — короткие случайные строки с префиксом по смыслу: `task_…`, `ver_…`,
`run_…`, `ses_…`, `acc_…`, `prv_…`, `etv_…`.

## Схема и миграции

Схему задают миграции Alembic в `common/storage/migrations/versions/`, пронумерованные
по порядку: `0001_baseline.py`, `0002_….py`. Номер текущей версии базы лежит в таблице
`alembic_version`.

- **Кто мигрирует.** Только main: при старте, до того как начать отвечать, он доводит
  схему до последней миграции. Остальные сервисы при старте ждут, пока схема станет
  текущей (до 60 секунд), и не запускаются на старой. Поэтому миграция никогда не идёт
  из двух процессов сразу.
- **Резервная копия.** Перед миграцией существующей базы main кладёт её копию в
  `DATA_DIR/backups/app-<версия>-<время>.db`; хранятся пять последних. Если миграция
  не удалась, базу можно вернуть из копии.
- **База из времени до миграций**, которую создал `create_all`, без `alembic_version`,
  считается версией `0001` и помечается ею без изменений.

Как изменить схему:

1. поменять модель в `common/storage/models.py`;
2. `python -m common.storage.migrate new "что поменялось"` — сгенерировать следующую
   миграцию. Она строится от пустой базы, доведённой до последней миграции, поэтому
   своя `data/app.db` разработчика на результат не влияет;
3. прочитать сгенерированный файл и поправить, если нужно: например, задать значение
   для новой `NOT NULL` колонки в уже существующих строках.

SQLite почти ничего не умеет менять в колонках на месте, поэтому миграции работают в
пакетном режиме Alembic: таблица пересоздаётся с новой схемой и данные копируются.
Тест `tests/test_migrations.py` падает, если модели и миграции расходятся.

## events

Лента событий: main сохраняет каждое и раздаёт подписчикам `GET /events`. Типы — в
[API.md](API.md#события). Старше [`retention_days`](SETTINGS.md) удаляются.

| Поле | Тип | Что это |
| --- | --- | --- |
| `id` | целое, PK | По возрастанию; по нему клиент догоняет пропущенное (`?since=`) |
| `type` | строка, индекс | Тип события |
| `payload` | JSON | Данные события |
| `created_at` | время | Когда |

## settings

Рабочие настройки, которые пользователь изменил через `PATCH /settings`. Нет строки —
действует значение по умолчанию; переменная окружения главнее строки. Сервисы читают
таблицу при каждом использовании настройки. Подробно — в [SETTINGS.md](SETTINGS.md).

| Поле | Тип | Что это |
| --- | --- | --- |
| `key` | строка, PK | Имя настройки, например `retention_days`; ещё `llm_chat`, `llm_instruct`, `llm_embed` — какой провайдер назначен на роль, их меняет `PATCH /llm`; `llm_env_imported` — какие модели из `LLM_*` уже заведены (см. [LLM.md](LLM.md#модели-из-переменных-окружения)) |
| `value` | JSON | Значение |
| `updated_at` | время | Когда изменено |

## llm_providers

Провайдеры LLM: каждый — одна модель на OpenAI-совместимом сервере. Какой провайдер
назначен на роль — в `settings`. Модели из `LLM_*` main заводит сюда при старте.
Подробно — в [LLM.md](LLM.md).

| Поле | Тип | Что это |
| --- | --- | --- |
| `id` | строка, PK | `prv_…`; под ним же ключ в хранилище ключей LLM |
| `name` | строка, уникальная | Название |
| `base_url` | строка | Адрес `/v1` |
| `model` | строка | Имя модели на сервере |
| `has_key` | да/нет | Есть ли ключ в хранилище |
| `created_at`, `updated_at` | время | Создан, изменён. `updated_at` меняется при любой правке, в том числе ключа: по нему сервисы понимают, что клиент надо пересоздать |

## chat_sessions

Чат задачи живёт, пока жива задача; временный agent-loop удаляет через
`chat_idle_hours` без сообщений вместе с его `chat_messages` и `trace_events` (см.
[CHAT.md](CHAT.md#сессии)). Чтобы отличить одно от другого, agent-loop читает `tasks` и
`task_versions`.

| Поле | Тип | Что это |
| --- | --- | --- |
| `id` | строка, PK | `ses_…` |
| `title` | строка | Первая строка первого сообщения (до 80 символов) |
| `created_at` | время | Создан |
| `updated_at` | время | Последнее сообщение; список чатов сортируется по нему |

## chat_messages

История чата, по которой модель видит разговор и из которой компилятор собирает
задачу.

| Поле | Тип | Что это |
| --- | --- | --- |
| `id` | целое, PK | Порядок сообщений |
| `session_id` | строка, индекс | Чат |
| `role` | строка | `user`, `assistant`, `tool` (результат команды для модели), `notice` (сообщение запуска задачи) |
| `content` | текст | Текст; результат команды — обрезанный до 6000 символов |
| `tool_calls` | JSON | Вызовы команд в сообщении `assistant` |
| `tool_call_id`, `name` | строка | К какому вызову относится сообщение `tool` |
| `created_at` | время | Когда |

## trace_events

Каждый вызов команды в чате с аргументами и полным результатом. По нему компилятор
понимает, что в разговоре удалось, а agent-loop — какое действие ждёт ответа
пользователя.

| Поле | Тип | Что это |
| --- | --- | --- |
| `id` | целое, PK | Он же `action_id` действия, ждущего ответа |
| `session_id` | строка, индекс | Чат |
| `message_id` | целое | Сообщение `assistant`, в котором был вызов |
| `tool` | строка | Команда; мета-инструменты — с префиксом `meta:` |
| `args` | JSON | Аргументы |
| `result` | JSON | Ответ executor (или мета-инструмента) |
| `status` | строка | `ok`, `error`, `needs_approval` (ждёт ответа пользователя), `confirmed` (выполнен после согласия) |
| `created_at` | время | Когда |

## tasks

| Поле | Тип | Что это |
| --- | --- | --- |
| `id` | строка, PK | `task_…` |
| `title`, `description` | строка, текст | Из активной версии (до одобрения — из первой) |
| `status` | строка, индекс | `draft`, `active`, `paused`, `archived` (см. [TASKS.md](TASKS.md#статусы)) |
| `current_version_id` | строка | Активная версия; пусто, пока ни одна не одобрена |
| `settings` | JSON | Что пользователь поменял в настройках команд, для всей задачи или шага: `{"mail": {"mail.send": {"send_directly": {"all": true, "steps": {"to_client": false}}}}}` (см. [TASKS.md](TASKS.md#настройки)) |
| `source_session_id` | строка | Чат, из которого задача собрана; туда приходят сообщения запусков |
| `created_at`, `updated_at` | время | Создана, изменена |

## task_versions

Неизменяемые снимки сценария. Любая правка — новая строка.

| Поле | Тип | Что это |
| --- | --- | --- |
| `id` | строка, PK | `ver_…` |
| `task_id` | строка, индекс | Задача |
| `version_no` | целое | 1, 2, 3… внутри задачи |
| `spec` | JSON | Сценарий (формат — в [TASKS.md](TASKS.md#формат)) |
| `status` | строка | `draft`, `approved`, `superseded`, `rejected` |
| `parent_version_id` | строка | От какой версии построена правка |
| `patch` | JSON | JSON Patch правки (для правки словами или `ops`) |
| `summary` | текст | Итог одной фразой |
| `cards` | JSON | Карточки шагов для человека |
| `tools` | JSON | Определение каждой команды шагов с его хешем: `{"fs.list": {"input_schema": …, "hash": "…"}}` — с ними версию одобряют (см. [TASKS.md](TASKS.md#команды-задачи)); `{}` у команды — версия из времён до хешей |
| `created_by` | строка | `compile`, `patch` (словами), `manual` (вручную) или `tools` (те же шаги с новыми определениями команд) |
| `session_id` | строка | Чат, из которого пришла версия; пусто для ручной правки |
| `created_at`, `approved_at` | время | Создана, одобрена |

## runs

| Поле | Тип | Что это |
| --- | --- | --- |
| `id` | строка, PK | `run_…` |
| `task_id` | строка, индекс | Задача |
| `task_version_id` | строка | Какая именно версия исполнялась |
| `trigger` | строка | `manual`, `cron` или `dry_run` |
| `status` | строка, индекс | `queued`, `running`, `succeeded`, `empty`, `failed`, `cancelled` (см. [RUNS.md](RUNS.md#статусы)) |
| `dry_run` | булево | Пробный запуск |
| `result` | JSON | Результат последнего шага и созданные файлы, или причина раннего окончания |
| `error` | текст | Почему упал |
| `started_at`, `finished_at` | время | Начат, закончен. Законченные старше `retention_days` удаляются вместе с журналом |

## run_log

Журнал запуска, записи только добавляются. Что в записях — в
[RUNS.md](RUNS.md#журнал-запуска).

| Поле | Тип | Что это |
| --- | --- | --- |
| `id` | целое, PK | — |
| `run_id` | строка, индекс | Запуск |
| `task_id` | строка, индекс | Задача |
| `seq` | целое | Порядок записи внутри запуска |
| `at` | время | Когда |
| `kind` | строка | `start`, `step`, `notify`, `end` |
| `step_key` | строка | Ключ шага, например `sort[2].move` |
| `data` | JSON | Содержимое записи |

## external_tools

Свои команды (`группа.действие`), строка на одобренный код и строка на черновик, см.
[EXTERNAL_TOOLS.md](EXTERNAL_TOOLS.md).

| Поле | Тип | Что это |
| --- | --- | --- |
| `id` | строка, PK | `etv_…` |
| `name`, `status` | строки; уникальны вместе | Команда; `current` — одобренный код, файлы заморожены, `draft` — черновик (один на команду, меняется на месте) |
| `hash` | строка | SHA-256 файлов без `.venv`; сверяется перед каждым вызовом |
| `manifest` | JSON | `tool.json` |
| `packages` | JSON | Точные пакеты из `requirements.lock`: `["six==1.17.0", …]` |
| `created_by` | строка | `user` или `chat` |
| `session_id` | строка | Чат, где черновик написали |
| `created_at`, `updated_at`, `approved_at` | время | Записан, изменён, одобрен |
