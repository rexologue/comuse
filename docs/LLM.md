# LLM

Этот документ описывает, как агент выбирает модели: роли, провайдеров, выбор текущего
провайдера, хранение ключей и проверку связи.

## Роли

Агент обращается к LLM в трёх ролях:

| Роль | Кто вызывает | Что нужно от модели |
| --- | --- | --- |
| `chat` | агент в чате, компилятор (сборка и правка задач словами) | вызов инструментов (`tools` / `tool_calls`), многошаговая работа |
| `instruct` | команды `llm.*`, разметка шаблонов в `docs.make_template` | одиночные структурированные ответы |
| `embed` | отбор команд под запрос | `/v1/embeddings`; без неё агент видит весь каталог |

Роль выбирается при каждом вызове, поэтому смена провайдера или модели действует без
перезапуска сервисов. Код — `common/llm.py`.

## Откуда берутся модели

Есть два режима.

**Из окружения.** Если задана `LLM_MODEL`, всё решают переменные `LLM_*` (см.
[DEPLOY.md](DEPLOY.md#переменные-окружения)). Выбор через API закреплён: `PATCH /llm`
отвечает `409`. В списке провайдеров этот набор показан как провайдер `env` с
`locked: true`. Так удобно в разработке и в Docker.

**Через API.** Если `LLM_MODEL` не задана, модели берутся из провайдеров, добавленных
через `/llm/providers`:

- **провайдер** — OpenAI-совместимый сервер со своими моделями для ролей;
- **текущий провайдер** обслуживает `chat` и `instruct`;
- **эмбеддинги** берутся у текущего провайдера, если для них не выбран другой. Так
  эмбеддинги могут жить на отдельном сервере.

Первый добавленный провайдер с моделью `chat` сразу становится текущим. Пока текущего
нет, сервисы работают, а чат на любое сообщение отвечает, как подключить модель.
Команды, которым модель не нужна, работают и без неё.

## Провайдер

| Поле | Что это | По умолчанию |
| --- | --- | --- |
| `name` | Название, уникальное | — |
| `base_url` | Адрес `/v1`, с `http://` или `https://` | — |
| `api_key` | Ключ; только на запись, API его не возвращает (`has_key` — есть ли он) | нет |
| `no_proxy` | Не брать прокси из `HTTP(S)_PROXY` | `true` |
| `timeout_sec` | Таймаут запроса | `300` |
| `max_retries` | Повторы при сетевых сбоях | `2` |
| `model_chat` | Модель роли `chat`. Пусто — провайдер только для эмбеддингов, текущим он быть не может | нет |
| `model_instruct` | Модель роли `instruct`. Пусто — та же, что `chat` | нет |
| `model_embed` | Модель эмбеддингов. Пусто — эмбеддингов у провайдера нет | нет |
| `reasoning_effort` | `low`, `medium` или `high` для модели `chat`. Пусто — не отправляется | нет |

Ключ хранится не в базе, а в отдельном хранилище ключей LLM (см.
[SECURITY.md](SECURITY.md#секреты)). Любое изменение провайдера, в том числе только
ключа, создаёт его новую версию: сервисы при следующем вызове строят новый клиент и
заново читают ключ.

## API

| Маршрут | Что делает |
| --- | --- |
| `GET /llm` | Провайдеры, текущий, провайдер эмбеддингов и что сейчас обслуживает каждую роль |
| `PATCH /llm` | `{"provider": id}` — сделать текущим, `{"embed_provider": id \| null}` — эмбеддинги от другого провайдера или от текущего |
| `POST /llm/providers` | Добавить провайдера |
| `PATCH /llm/providers/{id}` | Изменить; поля, которых нет в запросе, не меняются. `api_key: null` удаляет ключ |
| `DELETE /llm/providers/{id}` | Удалить; текущий удалить нельзя (`409`) — сначала выберите другой |
| `GET /llm/providers/{id}/models` | Модели, которые провайдер перечисляет в `/v1/models` |
| `POST /llm/providers/{id}/check` | Проверить модель каждой роли |

`GET /llm`:

```json
{
  "locked": false,
  "provider": "prv_1a2b3c4d5e6f",
  "embed_provider": null,
  "roles": {
    "chat": {"provider": "prv_1a2b3c4d5e6f", "model": "qwen3:30b"},
    "instruct": {"provider": "prv_1a2b3c4d5e6f", "model": "qwen3:30b"},
    "embed": {"provider": "prv_1a2b3c4d5e6f", "model": "bge-m3"}
  },
  "providers": [
    {"id": "prv_1a2b3c4d5e6f", "name": "Сервер команды", "base_url": "http://llm-host:8000/v1",
     "has_key": false, "no_proxy": true, "timeout_sec": 300, "max_retries": 2,
     "model_chat": "qwen3:30b", "model_instruct": null, "model_embed": "bge-m3",
     "reasoning_effort": null, "current": true, "embeddings": false, "locked": false,
     "created_at": "…", "updated_at": "…"}
  ]
}
```

`roles` — что обслуживает роль прямо сейчас, `null` — ничего.

**Проверка** вызывает модели по очереди; сбой одной не останавливает остальные:

- список моделей из `/v1/models`;
- `chat` — запрос с одним инструментом `ping`. Если модель ответила текстом, а не
  вызовом, проверка не пройдена: агенту нужен вызов инструментов;
- `instruct` — обычный короткий ответ;
- `embed` — эмбеддинг одной фразы, в ответе его размерность.

```json
{
  "ok": false,
  "list": {"ok": true, "models": ["bge-m3", "qwen3:30b"]},
  "roles": {
    "chat": {"model": "qwen3:30b", "ok": false, "error": "модель ответила текстом, а не вызовом функции: …"},
    "instruct": {"model": "qwen3:30b", "ok": true},
    "embed": {"model": "bge-m3", "ok": true, "dimensions": 1024}
  }
}
```

Проверка ждёт ответа не дольше 60 секунд на запрос и не повторяет запросы. Провайдер
`env` тоже можно проверить: `POST /llm/providers/env/check`, в том числе с отдельным
сервером эмбеддингов из `LLM_EMBED_BASE_URL`.

## Контракт

Нужен OpenAI-совместимый `POST /v1/chat/completions` с вызовом инструментов.
Остальное необязательно и имеет запасной путь:

- **Структурированный ответ.** Клиент пробует `json_schema`, затем `json_object`,
  затем обычный текст со схемой в промпте и запоминает, что сработало для модели.
- **Эмбеддинги** (`/v1/embeddings`) нужны только для отбора команд.
- **`reasoning_effort`** отправляется, только если задан.
- **`/v1/models`** нужен только проверке и списку моделей.
