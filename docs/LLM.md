# LLM

Этот документ описывает, как агент выбирает модели: роли, провайдеров, назначение
ролей с проверкой и модели из переменных окружения.

## Роли

Агент обращается к LLM в трёх ролях:

| Роль | Кто вызывает | Что нужно от модели |
| --- | --- | --- |
| `chat` | агент в чате, компилятор (сборка и правка задач словами) | вызов инструментов (`tools` / `tool_calls`), многошаговая работа |
| `instruct` | команды `llm.*` | одиночные структурированные ответы. Не назначена — работает модель `chat` |
| `embed` | отбор команд под запрос | `/v1/embeddings`. Не назначена — агент видит весь каталог команд |

Модель для роли определяется при каждом вызове, поэтому новое назначение действует
без перезапуска сервисов. Код — `common/llm.py`.

Пока на `chat` ничего не назначено, сервисы работают, а чат на любое сообщение
отвечает, как подключить модель. Команды, которым модель не нужна, работают и без неё.

## Провайдер

Провайдер — это одна модель на OpenAI-совместимом сервере:

| Поле | Что это |
| --- | --- |
| `name` | Название, уникальное |
| `base_url` | Адрес `/v1`, с `http://` или `https://` |
| `model` | Имя модели на этом сервере |
| `api_key` | Ключ; только на запись, API его не возвращает (`has_key` — есть ли он) |

Две модели на одном сервере — это два провайдера. На любую роль можно назначить любого
провайдера.

Ключ хранится не в базе, а в отдельном хранилище ключей LLM (см.
[SECURITY.md](SECURITY.md#секреты)). Любая правка провайдера, в том числе только
ключа, создаёт его новую версию: сервисы при следующем вызове строят новый клиент и
заново читают ключ.

Общие для всех провайдеров параметры — рабочие настройки (см. [SETTINGS.md](SETTINGS.md)):
`llm_timeout_sec`, `llm_max_retries`, `llm_no_proxy`. У ролей `chat` и `instruct` свой
сэмплинг: `llm_<роль>_temperature`, `llm_<роль>_top_p`, `llm_<роль>_thinking` (`on` / `off`
— `chat_template_kwargs.enable_thinking`, его понимают vLLM, SGLang и llama.cpp) и
`llm_<роль>_reasoning_effort`. Пустое значение не отправляется: работает значение сервера,
и сервер, который не знает поля, о нём не спрашивают. Сэмплинг относится к роли, а не к
провайдеру: одна модель может служить обеим ролям, а нужно им разное (чату рассуждения
полезны, разметке и извлечению полей — обычно нет).

## Назначение и проверка

`PATCH /llm` назначает провайдеров на роли. Перед назначением каждый провайдер
проверяется на свою роль:

- `chat` — запрос с одним инструментом `ping` и текущим сэмплингом роли `chat`.
  Если модель ответила текстом, а не вызовом, проверка не пройдена: агенту нужен вызов
  инструментов;
- `instruct` — обычный короткий ответ;
- `embed` — эмбеддинг одной фразы.

Если не прошла хоть одна проверка, не меняется ни одна роль, а ответ `400` называет
причину по каждой роли. `null` снимает назначение. Без назначения `instruct` снова
работает на модели `chat`.

Проверка ждёт ответа не дольше 60 секунд и не повторяет запрос. Её можно запустить и
отдельно: `POST /llm/providers/{id}/check` с `{"role": "chat"}`.

## Модели из переменных окружения

Если задана `LLM_MODEL`, main при старте заводит модели из `LLM_*` обычными
провайдерами (`main/providers.py`):

| Провайдер | Модель | Роль |
| --- | --- | --- |
| `default` | `LLM_MODEL_CHAT` или `LLM_MODEL` | `chat` |
| `default-instruct` — только если модель другая | `LLM_MODEL_INSTRUCT` | `instruct` |
| `default-embed` — если задана `LLM_MODEL_EMBED` | `LLM_MODEL_EMBED` на `LLM_EMBED_BASE_URL` | `embed` |

- Каждая пара «адрес + модель» импортируется один раз: main запоминает её в строке
  `llm_env_imported` таблицы `settings`. Поэтому провайдера можно переименовать,
  перенести на другой адрес или удалить — при следующем старте он не появится снова.
  Новая модель или адрес в `LLM_*` заводятся при следующем старте.
- Если такой адрес с такой моделью уже есть (даже под другим названием), новый
  провайдер не заводится, а используется этот.
- Роль назначается, только если она ещё пустая. Проверка при этом не выполняется: старт
  не должен зависеть от того, доступна ли модель.
- Если название занято другой моделью, к нему добавляется номер: `default 2`.
- Ключ (`LLM_API_KEY`, `LLM_EMBED_API_KEY`) уходит в хранилище ключей LLM.

Дальше это обычные провайдеры: их можно менять, удалять и назначать, а рядом
добавлять другие.

## API

| Маршрут | Что делает |
| --- | --- |
| `GET /llm` | Провайдеры и кто обслуживает каждую роль |
| `PATCH /llm` | `{"chat": id, "instruct": id \| null, "embed": id \| null}` — назначить с проверкой; роли, которых нет в запросе, не меняются |
| `POST /llm/providers` | Добавить провайдера: `name`, `base_url`, `model`, `api_key` |
| `PATCH /llm/providers/{id}` | Изменить; поля, которых нет в запросе, не меняются. `api_key: null` удаляет ключ |
| `DELETE /llm/providers/{id}` | Удалить; назначенного на роль — нельзя (`409`) |
| `POST /llm/models` | Модели сервера из `/v1/models`: `{"base_url", "api_key"}` или `{"provider": id}` |
| `POST /llm/providers/{id}/check` | Проверить провайдера на роль: `{"role": "chat"}` |

`GET /llm`:

```json
{
  "roles": {
    "chat": {"provider": "prv_1a2b3c4d5e6f", "name": "default", "model": "qwen3:30b"},
    "instruct": {"provider": "prv_1a2b3c4d5e6f", "name": "default", "model": "qwen3:30b", "follows_chat": true},
    "embed": {"provider": "prv_6f5e4d3c2b1a", "name": "default-embed", "model": "bge-m3"}
  },
  "providers": [
    {"id": "prv_1a2b3c4d5e6f", "name": "default", "base_url": "http://llm-host:8000/v1",
     "model": "qwen3:30b", "has_key": false, "roles": ["chat", "instruct"],
     "created_at": "…", "updated_at": "…"},
    {"id": "prv_6f5e4d3c2b1a", "name": "default-embed", "base_url": "http://llm-host:8000/v1",
     "model": "bge-m3", "has_key": false, "roles": ["embed"],
     "created_at": "…", "updated_at": "…"}
  ]
}
```

`null` у роли — ничего не назначено. `follows_chat` — у `instruct` нет своего
назначения, работает модель `chat`.

Неудачное назначение:

```json
{"error": {"code": "BAD_REQUEST", "message": "Роли не изменены: проверка не пройдена",
           "details": {"chat": "default-embed: LLM responded with HTTP 400"}}}
```

Проверка провайдера:

```json
{"role": "embed", "model": "bge-m3", "ok": true, "dimensions": 1024}
```

## Контракт

Нужен OpenAI-совместимый `POST /v1/chat/completions` с вызовом инструментов.
Остальное необязательно и имеет запасной путь:

- **Структурированный ответ.** Клиент пробует `json_schema`, затем `json_object`,
  затем обычный текст со схемой в промпте и запоминает, что сработало для модели.
- **Эмбеддинги** (`/v1/embeddings`) нужны только для отбора команд.
- **`reasoning_effort`** отправляется, только если задан.
- **`/v1/models`** нужен только для списка моделей в `POST /llm/models`.
