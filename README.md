# fintech2026 · офисный агент

Пользователь объясняет работу в обычном чате: «вот пример отчёта, сделай такой же
за прошлую неделю». Агент делает её через команды (файлы, документы, таблицы,
почта), а по просьбе «делай так каждый понедельник» собирает разговор в задачу —
замороженный сценарий из конкретных шагов. Пользователь один раз одобряет задачу,
дальше она исполняется по расписанию или по кнопке без LLM-планирования.

Агент:

- работает с любым OpenAI-совместимым `/v1` с вызовом инструментов; модели задаются
  только конфигом;
- сам отвечает как OpenAI-совместимый чат (`/v1/chat/completions`), поэтому к нему
  подключается любой клиент стандарта, включая готовые чат-интерфейсы;
- перед каждой командой, которая что-то меняет, спрашивает пользователя; ответ
  засчитывается, только если пользователь его действительно написал;
- собирает из чата задачу и проверяет её по каталогу команд, ничего при этом не
  запуская: решение — пробный запуск, правка или одобрение — за пользователем;
- исполняет задачи шаг за шагом, никогда не ждёт человека и пишет по каждому запуску
  один журнал: аргументы, результаты, ошибки, сообщения пользователю;
- держит пароли в системном хранилище секретов (в Docker — в зашифрованном файле): ни
  модель, ни задачи их не видят, только имя аккаунта.

## Структура

```text
main/            шлюз: внешний API, реестр сервисов, одобрения, уведомления, события (SSE)
agent_loop/      чат: цикл «LLM → команды», вопросы перед действиями, история
compiler/        чат → задача, проверки, правки (словами через LLM или вручную)
runner/          исполнение задачи по шагам и журнал запуска
executor/        единственное место, где выполняются команды: аргументы, пути, секреты
scheduler/       cron: только «когда запускать»
internal_tools/  команды по группам: fs, docs, xlsx, data, mail, charts, llm, user
common/          общий код: настройки, схемы, БД, клиенты, каркас команд
deploy/          docker compose и шаблон настроек для него
misc/            демо-данные для сценария еженедельного отчёта
single_app.py    все сервисы в одном процессе (RUN_MODE=single)
web/             веб-интерфейс: клиент API main
docs/            справочники
```

Это шесть отдельных сервисов, и все вызовы между ними идут через `main` по HTTP:
сервисы знают только его адрес. Локально они по умолчанию работают в одном процессе
на одном порту (`single_app.py`, около 130 МБ памяти вместо примерно 690 МБ у шести
процессов), в Docker — по контейнеру на сервис; код и границы одни и те же. Так у каждого сервиса одна зона ответственности, которую он
не делит с другими: scheduler знает «когда», runner — «в каком порядке», executor —
«чем», а что значат почта, файлы и отчёты, знают только сами группы команд в
`internal_tools/`. Хранилище — один файл SQLite, у каждой таблицы ровно один
сервис-владелец, который в неё пишет.

## Запуск

Зависимости ставятся в `.venv` проекта:

```bash
uv sync --extra dev
```

Настройки: скопируйте шаблон и укажите адрес LLM и модель — при старте они станут
провайдером `default`. Можно оставить `LLM_*` пустыми и подключить модель потом через
API (`POST /llm/providers`, см. [LLM](docs/LLM.md)).

```bash
cp .env.example .env
```

Демо-папка для сценария отчёта (пример отчёта и выгрузки продаж по неделям):

```bash
uv run python misc/make_demo_data.py workspace
```

Все шесть сервисов, логи в одной консоли:

```bash
uv run python launcher.py
```

Адрес API launcher печатает при старте (`API at http://127.0.0.1:<порт>`) и пишет в
`data/runtime.json`. Порт у main постоянный: свободный, выбранный при первом запуске,
или `MAIN_PORT` из `.env`. Остальные сервисы берут любые свободные порты. Второй
launcher с той же папкой данных не запустится. Интерактивная документация —
`<адрес>/docs`. Каждому запросу нужен токен: `API_TOKEN` из `.env` или, если он пуст,
тот, что main создал в `data/api_token`. Первое сообщение (с `MAIN_PORT=8000`):

```bash
curl -s -X POST localhost:8000/agent/v1/chat/completions -H "Authorization: Bearer $(cat data/api_token)" -H 'content-type: application/json' -d '{"messages":[{"role":"user","content":"В папке Отчёты/Пример лежит пример еженедельного отчёта. Сделай такой же за прошлую неделю по выгрузкам из Отчёты/Продажи."}]}'
```

Ответ содержит `session_id`: передавайте его дальше в `metadata.session_id`. Клиент,
который про него не знает и просто присылает всю переписку, тоже попадёт в свой чат —
см. [Чат](docs/CHAT.md).

В Docker — один образ, по контейнеру на сервис, наружу открыт только `main`:

```bash
cp deploy/.env.example deploy/.env
```

```bash
docker compose -f deploy/docker-compose.yaml up -d --build
```

Для разработки — весь агент в одном контейнере с перезапуском при правке кода (настройки
из `.env` в корне) и веб-интерфейс на `http://localhost:5173` (см. [Фронт](docs/WEB.md)):

```bash
docker compose -f deploy/compose.dev.yaml up --build
```

Тесты:

```bash
uv run pytest
```

Подробности, в том числе про Windows и хранение секретов, — в
[Развёртывании](docs/DEPLOY.md).

## LLM

Нужен OpenAI-совместимый `POST /v1/chat/completions` с вызовом инструментов
(`tools` / `tool_calls`). Структурированный ответ, эмбеддинги и `reasoning_effort`
необязательны и имеют запасной путь.

Модели работают в трёх ролях: `chat` (агент и сборка задач), `instruct` (команды
`llm.*` и разметка шаблонов; не назначена — работает `chat`), `embed` (отбор команд;
не назначена — агент видит все). Провайдер — это одна модель на сервере: адрес, ключ,
имя модели и название. На любую роль назначается любой провайдер, и перед назначением
он проверяется на эту роль: для `chat` — что модель вызывает инструменты, для `embed` —
что возвращает эмбеддинг. Модели из `LLM_*` при старте становятся провайдерами
`default…`. Новое назначение действует без перезапуска.

Подробности — в [LLM](docs/LLM.md).

## Важные переменные окружения

| Переменная | Значение | По умолчанию |
| --- | --- | --- |
| `LLM_BASE_URL` | Адрес OpenAI-совместимого `/v1` | `http://127.0.0.1:11434/v1` |
| `LLM_MODEL` | Модель на всё; при старте становится провайдером `default` | не задано |
| `LLM_MODEL_CHAT`, `LLM_MODEL_INSTRUCT` | Модели по ролям | `LLM_MODEL` |
| `LLM_MODEL_EMBED` | Модель эмбеддингов | не задано |
| `DATA_DIR` | База, шаблоны, готовые файлы | `data` |
| `API_TOKEN` | Токен внешнего API, нужен всегда; пусто — main создаёт его в `data/api_token` | не задано |
| `INTERNAL_TOKEN` | Токен между сервисами; локально его создаёт `launcher.py` | не задано |
| `KEYRING_BACKEND` | Где пароли аккаунтов: `system` или `file` | `system` |

Полная таблица — в [Развёртывании](docs/DEPLOY.md). Рабочую папку, сроки хранения и
параметры агента можно менять, не перезапуская агент, через `PATCH /settings` — см.
[Настройки](docs/SETTINGS.md).

## Чат

Чат — это запись работы: агент пробует, показывает результат, пользователь
поправляет. Команды, которые только смотрят и считают, агент вызывает сам; перед
каждой, что что-то меняет (переложить файл, пометить или отправить письмо), — задаёт
вопрос и ждёт ответа. Пользователь может ответить «да, и больше не спрашивай про это
в этом чате»; отправка писем спрашивает всегда. Подробности — в [Чате](docs/CHAT.md).

## Задачи

По просьбе «формируй задачу» компилятор собирает из разговора сценарий: шаги с
командами и аргументами, данные между шагами передаются шаблонами
(`{{ files.output.files }}`), даты — фильтрами (`{{ today | start_of_prev_week }}`).
Задача проверяется по каталогу команд и уходит в чат черновиком. Включает её только
сам пользователь. Каждая правка — новая версия с diff и тем же одобрением.
Подробности — в [Задачах](docs/TASKS.md).

## Запуски

Scheduler запускает задачу по cron, пользователь — по кнопке. Runner идёт по шагам от
начала до конца, ошибки и пустые результаты обрабатывает по правилам шага и пишет всё
в журнал запуска. Где нужен человек, задача оставляет результат вне запуска: письмо в
черновиках, файл в папке. Пробный запуск исполняет черновик, а команды, которые
что-то меняют, в нём только пишут, что сделали бы. Подробности — в
[Запусках](docs/RUNS.md).
